# 03 · 关账与发布闸门

本节规定什么情况下可以继续实施、提交或上传。具体口令和 git 步骤写在 `ZL01_具体说明/09-上传流程.md` 与对应 playbook，本页不复制操作细节。

## 实施闸门

正式按规格或工作包实施前，必须同时满足：

- 没有未裁决的相关冲突；
- 若决定已经批准，结论已回写到真正的权威文件；
- 范围文件（允许改什么、禁止改什么）明确；
- 不把未跟踪的本机工具目录或密钥材料纳入工作区“准备入库”的范围。
- 暂存区出现计划外文件、保护路径出现计划外差异时，停止受影响实施或上传。

“已经接受但尚未回写”的状态，会阻止受影响范围的正式实施。

创建下一产品热修分支前，只核对与新分支**实际依赖的基线**有关的治理决定和代码。前置方法若必须成为该基线的一部分，应先验收并按用户授权集成；独立于新分支的未上传方法草稿不构成全局禁令，也不得被夹带。分支创建、提交和上传各按用户已给出的具体操作范围执行，不因阶段编号重复索权。

## 提交与上传闸门

听到需要入库或上传时：

1. 用户必须明确授权提交/上传的目标分支和操作范围。可在同一指令中预先授权验收后的连续提交、推送与远端复核；验收通过本身不等于授权，已授权的同一操作也不必反复询问。
2. 对照范围只覆盖准备入库的差异，不顺手做全仓重构。
3. 上传前可以写好制度、说明和已知事实；不得把尚未发生的提交 hash、远端一致或“已经上传成功”写成既成事实。
4. 只能按显式文件路径暂存。禁止用会吞进未跟踪 `tools/` 或其他无关目录的通配命令。
5. 只有确需把“实际上传之后才知道的事实”记入仓库，且记录文件属于已授权范围时，才在内容成功上传后另做记账提交；不强制 A/B、固定文件清单或为记账提交再记账。真实 SHA 与远端结果也可先在本次任务报告中核对，不得预填成功。
6. 默认不改 `main`、不移动已有 release tag、不 force push、不创建未授权的新分支。

失败时停止并准确报告已成功和未成功的部分，不靠重写历史或伪造记录来“补齐”。

## 外部与设备验收

- Apple Sandbox、退款网页或其他第三方服务不可用时，记录时间、设备、网络和原始现象；有限重试后标成“未验证／延期风险”，不能把自动测试或购买成功推论成退款撤权通过。只有用户明确接受改变本次验收条件，才可在保留发布前风险的前提下关本阶段。
- 真机覆盖安装、替换重装或清除前，先确认安装方式、备份是否可恢复、备份不包含的系统钥匙串／设备偏好，以及可能丢失的本机数据；风险未被用户接受时不得进行破坏性安装。测试包与正式发布包必须分别标识。
- 一次异常退出若不可复现，记录测试次数、日志及未解释边界；可由用户接受残余风险，但不得写成“已找到根因”。

## 关账闸门

一个工作包或小迭代关账前必须完成：

- 来源确认（Spec Kit 还是 ZL02）；
- 决定记录；
- 权威回写；
- ZL01 当前状态按已核实事实更新，并标明核对日期与适用分支；无法核实时明确写“待核对”，不得沿用旧快照冒称当前；
- 链接与路牌检查。

关账后的过程档案留在原路径，用文件内状态表示完成，不靠搬家表示归档。
