# 03 · 关账与发布闸门

本节规定什么情况下可以继续实施、提交或上传。具体口令和 git 步骤写在 `ZL01_具体说明/09-上传流程.md` 与对应 playbook，本页不复制操作细节。

## 实施闸门

正式按规格或工作包实施前，必须同时满足：

- 没有未裁决的相关冲突；
- 若决定已经批准，结论已回写到真正的权威文件；
- 范围文件（允许改什么、禁止改什么）明确；
- 不把未跟踪的本机工具目录或密钥材料纳入工作区“准备入库”的范围。
- 暂存区出现计划外文件、保护路径出现计划外差异时，停止受影响实施或上传。

“已经接受但尚未回写”的状态，会阻止受影响范围的正式实施。

创建下一产品热修分支前，**确实构成该分支前置依赖**的方法或治理工作须已通过适当验证、完成本次授权范围内的提交上传及远端核对。无依赖的旧工作包不阻断新分支；不得夹带尚未归属的本地方法草稿开新线。只有一个 AI 实际参与时不得把自查称为独立复核。

## 提交与上传闸门

听到需要入库或上传时：

1. 用户必须明确授权本次提交/上传。验收通过不等于授权上传。
2. 对照范围只覆盖准备入库的差异，不顺手做全仓重构。
3. 上传前可以写好制度、说明和已知事实；不得把尚未发生的提交 hash、远端一致或“已经上传成功”写成既成事实。
4. 按 [`06-方法迭代闭环.md`](./06-方法迭代闭环.md) 检查本次是否出现方法缺陷；按新版方法建立且授权范围包含阶段记录的标准/高风险工作包，须有本次阶段记录及其只读检查结果。封闭文件清单不含记录或索引时按 `06` 留明白的欠项，不越界补文件；非阻塞方法欠项不机械挡住无关产品提交。旧工作包不倒填新记录；此项不把外部服务待验证改称通过。
5. 只能按显式文件路径暂存。禁止用会吞进未跟踪 `tools/` 或其他无关目录的通配命令。
6. 若制度要求把“实际上传之后才知道的事实”记入仓库，这些事实必须放在内容提交成功上传之后的单独记账步骤，并且该记账步骤不得再派生新的上传记录。
7. 默认不改 `main`、不移动已有 release tag、不 force push、不创建未授权的新分支。

失败时停止并准确报告已成功和未成功的部分，不靠重写历史或伪造记录来“补齐”。

## 关账闸门

一个工作包或小迭代关账前必须完成：

- 来源确认（Spec Kit 还是 ZL02）；
- 决定记录；
- 权威回写；
- ZL01 当前状态更新；
- 链接与路牌检查。
- 适用时按 [`06`](./06-方法迭代闭环.md) 完成阶段方法记录及本次阻塞方法缺陷的修正和复验；精确授权范围排除记录时明示欠项，不冒称文件化闭环完成。单 AI 自查不得写成独立验收。

关账后的过程档案留在原路径，用文件内状态表示完成，不靠搬家表示归档。
