# 02 · 冲突裁决与变更机制

发现 Spec Kit、ZL01、ZL02、AI 对话、开发流程或上传流程互相矛盾时，先停止受影响的正式实施或上传，再按本节处理。

## 固定顺序

1. **停止**：只停受冲突影响的动作，不扩大到无关工作。
2. **分类**：这是治理问题、产品内容问题，还是某次工作的执行事实？分类标准见 [`01-权威职责与边界.md`](./01-权威职责与边界.md)。
3. **收集证据**：保存冲突原文、路径、日期和相关对话索引。AI 对话只作证据，不作决定。
4. **拟方案**：说明保留现状还是改变方案，以及将回写哪些权威文件。
5. **批准**：日常文档去重可由维护者按已有规则处理。涉及战略、版本归属、安全边界、发布或不可逆操作，必须由用户批准。
6. **回写**：把获批结论写进真正负责该类内容的文件；过程证据留在原来的工作来源（Spec Kit 或 ZL02）。
7. **更新中文状态**：只更新 [`ZL01_具体说明/14-项目当前状态.md`](../ZL01_具体说明/14-项目当前状态.md) 中受影响的当前说法。
8. **一致性检查**：受影响链接、路牌和索引不再指向互相打架的结论后，才恢复实施或发布。

## 决定记录至少包含

- 冲突是什么、出现在哪些文件；
- 证据在哪里；
- 采用哪一种方案、不采用哪一种；
- 由谁批准；
- 回写到哪一份正式权威；
- ZL01/14 是否已更新。

紧急事故允许先止血，但必须事后补做裁决和回写。未完成回写前，受影响范围不得当成已经关账。

## Spec Kit 与 ZL02 的双向反馈

- Spec Kit 实施中发现规格不适用：在对应 spec 中记录问题和候选变更，不得只在 ZL02 另写一套长期有效的替代规格。
- 使用后的非 Spec Kit 调整发现主体结构必须变化：在 ZL02 工作包记录问题、证据、方案、实施和审计；用户批准改变正式产品结构后，再回写 spec / ROADMAP / 宪法。
- 关账前必须消除“两边各有一个现行答案”。允许实践改变原计划，不允许两个答案同时自称有效。
