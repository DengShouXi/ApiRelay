<h2 id="save-changes">§1 · 听到「上传」时按这个顺序</h2>

日常对 Cursor 说 **「上传」** 即可；它只表示本次准备入库的范围和目标分支，不能推定 `v1`、`main`、tag、商店送审或设备操作也获授权。下列口令走同一段：

```text
上传
保存并上传
按热修-save 保存并上传
```

单独说「提交」只授权本地 commit，**不自动 push**；单独说「保存」只保存文件，不自动 Git 提交或推送。只有「上传」「推送」「保存并上传」等明确远程意图才进入 push。已有明确的连续授权按原范围执行，不因换 AI 或阶段名称重复询问。

顺序固定为 **对照 → 同步本夹 → git**。先 push 再对照，冲突就要再传一次；先写说明再改代码，说明会写两遍。

开新小阶段（`P0N-save` → `plan.N` / `v1.N` / `v2.N`）见 [`07` §2](./07-计划流程.md#planning-steps)。走哪份 save 之前，仍先做完下面三步；不要用热修口令冒充新 Phase。

<h3 id="save-step-align">§1.1 · 对照本次 diff 与相关规格</h3>

只对**这次准备入库的 diff** 对照它们引用的 `spec.md` / `data-model.md` / 宪法 / 相关 playbook。用户划了范围（例如「只传流程文档」）则只对照该范围；工作区里留给下一热修的文件不纳入。MUST NOT 借「上传」做全仓审计或顺手重构。

| 对照结果 | 怎么处理 |
|---|---|
| 代码违反**仍生效**的规格 | 在这次上传对话里改到对齐（允许，且只改这件事） |
| 决策其实变了，要动宪法 / `spec.md` / `ROADMAP.md` | **停下来说明，等用户确认**。MUST NOT 擅自改决策文件 |
| 规格仍对，只是本夹摘要旧了 | 交给 [§1.2](#save-step-zl01) |
| 没有矛盾 | 完成汇报里写一句「对照过、无矛盾」，不要静默跳过 |

这次若留下一条看起来像正式设计、其实是权宜的路径，后面按计划推进时会把它当样板。要么改到符合仍生效的计划，要么在规格里写成**明确例外**（只此一次、不得当样板）。不要既不改、也不写。

本次为对齐改了代码（或本来就有未提交代码）：进入 [§1.3](#save-step-git) 前跑 `bash ApiRelay/scripts/selfcheck.sh`；红线失败 MUST NOT push。改了代码的收尾四问仍要回答（[`.cursor/rules/implementation-closeout.mdc`](../.cursor/rules/implementation-closeout.mdc)），不要用「已经上传」代替。纯说明改动按 [`12`](./12-通用格式要求.md) 验收链接与目录即可。

按路由表，**有改才动**；没碰到的页 MUST NOT 重写。本夹继续当路牌，不把 FR、模型字段、hash 再抄一份。

| 这次实际改了什么 | 才去动哪一页 |
|---|---|
| 源码文件增删 / 搬家 | [`02`](./02-代码地图.md) |
| 路径、CloudKit、不可逆约束 | [`03`](./03-路径红线.md) |

| 计划 / 开发 / 上传步骤 | [`07`](./07-计划流程.md) / [`08`](./08-开发流程.md) / 本页 |

<h3 id="save-step-git">§1.3 · 再 git</h3>

提交次数由本次授权范围和实际记录需要决定，**不固定为 A/B 两次**。内容提交与只有上传后才知道的事实必须分开；没有后置记账需要时不制造空提交。闸门见 [`ZL00` 关账与发布](../ZL00_项目总控/03-关账与发布闸门.md)。

1. `git status` 与 `git diff`：用几句人话写出变化。用户划了范围则只处理该范围。  
2. 判断走哪份 save，**不要问用户再解释一遍分支策略**：  
   - 规划或产品小阶段（对应 P0N 尚未关账）→ 该目录 `P0N-save.md`  
   - 已关账小迭代上的修 bug / 上架后热修（当前默认）→ [`热修-save.md`](../ApiRelay/specs/playbooks/热修-save.md)  
   已经在正确的热修分支上（例如正在 `v1.13.8`），**不要再开一条**。  
3. **内容提交**：只按**显式路径**逐个 `git add`。禁止 `git add .`、`git add -A` 或会吞进无关目录的通配。不得把尚未发生的 SHA、远端一致或“已上传”写成事实。只推送已获授权的目标分支；若只授权本地提交则止于 commit。失败时准确报告部分结果。
4. **后置记账（确有需要时）**：内容提交已成功推送并核对远端后，才把真实 SHA 和结果写进本次批准的工作包或实际需要更新的状态页。只显式暂存获准路径，单独提交／推送；不为记账提交自身无限追加尾单。若无后置事实需要入库，就不做第二次提交。
5. 大阶段 tip（`v1` / `v2` / `v3`）**默认不移动**。只有用户明确授权该引用，且目标 SHA 与关账条件已核对，才单独快进并核对远端；热修分支上传绝不自动包含这一步。
6. 没有可入库改动、对照与同步也无事可做 → 不空 commit。

<h3 id="save-bounds">§1.4 · 边界</h3>

- 对照范围 = 这次准备入库的 diff，不是整份 `spec` 对整仓。  
- 工作区若混有下一热修的未提交改动：只入库用户划定的范围，其余原样留在工作区带到下一分支。  
- 发现无关优化：只报告，不改。  
- `*.vsix`、`tools/` 下的安装包、`ZL03_原始素材/` 下的大文件、`DebugScratch/`、`build/`、密钥、`.env`、含真实密钥的截图不入库。  
- 未获明确本地提交或上传授权前 MUST NOT commit；单独「保存」不是 Git 授权。
- 默认不 push `main`、不打 tag、不 force push、不改 `MARKETING_VERSION`。

<h2 id="testflight">§3 · 用当前分支测试发布</h2>

TestFlight 内测、Archive 上传和 App Store「提交以供审核」是不同操作，分别核对授权。执行前读取目标分支、Xcode 当前 `MARKETING_VERSION`／构建号、Organizer 产物、ASC 已处理构建和相应工作包的验收要求；**不要用本页旧数字选包**。Mac Catalyst 与 iOS 产物分别确认平台与签名，Debug Run 包不能冒充 TestFlight 验收包。

真机覆盖安装前按 [`ZL00/03`](../ZL00_项目总控/03-关账与发布闸门.md#外部与设备验收) 核对备份和钥匙串边界。付费验收应分别记录真实购买、取消、冷启动恢复、手动恢复、退款撤权、跨设备状态；Apple 服务不可用的项标成未验证风险，不能因其他项通过就勾选。不要使用真实密钥做演示数据。

具体 TestFlight 界面步骤见 [`P13-人工操作指南/06-TestFlight内测.md`](../ApiRelay/specs/playbooks/v1-key-vault/phases/P13-人工操作指南/06-TestFlight内测.md)，其中历史示例版本号须以现场为准。未获明确授权，不推 `main`、不打发布 tag、不点击 ASC 送审。

<h2 id="upload-notes">§4 · 备注写什么</h2>

实际上传成功后才写上传结果；内容提交中不得预填“已经上传”。记录位置只取本次已批准且实际受影响的文件。

| 写哪 | 何时写 | 写什么 | 不要写什么 |
|---|---|---|---|
| 本次工作包上传记录 | 内容提交推送并核对后，且工作包要求时 | 实际提交和远端 SHA、文件范围、测试及未覆盖项 | 预填结果或把保全上传称为正式验收 |
| [`13`](./13-上传记录.md) | 本次范围要求中文流水账时 | 日期、分支和已确认的上传事实 | 未发生的推送或重复完整技术报告 |
| [`10`](./10-AI对话相关记录.md) | 对话索引确需同步时 | 已确认的进展 | 虚构 UUID；预填最终复核通过 |
| [`14`](./14-项目当前状态.md) | 当前状态发生变化时 | 核对日期、适用分支、已上传与未验收边界 | 把旧分支快照当全仓当前状态 |
| [`BRANCHES.md`](../ApiRelay/specs/playbooks/BRANCHES.md) | 分支台账纳入本次范围时 | 按既有格式记录真实内容 tip | 把记账提交误当内容 tip |

`13` 同一条热修线上可以多行；需要更新时，新行接在对应节**最末尾**。写法见 [`13` §1](./13-上传记录.md#how-to-log)。后置记账不为自身再派生一笔尾单。

<h2 id="maintenance">§6 · 维护</h2>

- 听到「上传」的**完整正文只改本页 [§1](#save-changes)**。`热修-save.md` 只保留分支与保护引用；Cursor 规则只负责路由。三处不再复制提交步骤。
- 当前任务只改 [`14`](./14-项目当前状态.md)，不要在本页 §2 再抄一份「正在做什么」。  
- 关账／开热修后，把**已核实**的适用工作树、日期和状态写进 [`14`](./14-项目当前状态.md)；本页 §2／§3 保持不含动态版本数字的操作说明。

- 实际上传记录在内容推送成功并核对后按 [§4](#upload-notes) 更新；不要在 git 之前假装已经 push。
