<h2 id="save-changes">§1 · 听到「上传」时按这个顺序</h2>

日常对 Cursor 说 **「上传」** 即可。下列口令走同一段，不必再念三件事，也不必再贴 `热修-save` 全文：

```text
上传
保存并上传
按热修-save 保存并上传
```

「提交 / 保存」与上表同效（仍会 push；现行热修 save 没有「只 commit 不推远程」）。

顺序固定为 **对照 → 同步本夹 → git**。先 push 再对照，冲突就要再传一次；先写说明再改代码，说明会写两遍。

开新小阶段（`P0N-save` → `plan.N` / `v1.N` / `v2.N`）见 [`07` §2](./07-计划流程.md#planning-steps)。走哪份 save 之前，仍先做完下面三步；不要用热修口令冒充新 Phase。

<h3 id="save-step-align">§1.1 · 对照本次 diff 与相关规格</h3>

只对**这次准备入库的 diff** 对照它们引用的 `spec.md` / `data-model.md` / 宪法 / 相关 playbook。用户划了范围（例如「只传流程文档」）则只对照该范围；工作区里留给下一热修的文件不纳入。MUST NOT 借「上传」做全仓审计或顺手重构。

| 对照结果 | 怎么处理 |
|---|---|
| 代码违反**仍生效**的规格 | 在这次上传对话里改到对齐（允许，且只改这件事） |
| 决策其实变了，要动宪法 / `spec.md` / `ROADMAP.md` | **停下来说明，等用户确认**。MUST NOT 擅自改决策文件 |
| 规格仍对，只是本夹摘要旧了 | 交给 [§1.2](#save-step-zl01) |
| 没有矛盾 | 完成汇报里写一句「对照过、无矛盾」，不要静默跳过 |

这次若留下一条看起来像正式设计、其实是权宜的路径，后面按计划推进时会把它当样板。要么改到符合仍生效的计划，要么在规格里写成**明确例外**（只此一次、不得当样板）。不要既不改、也不写。

本次为对齐改了代码（或本来就有未提交代码）：进入 [§1.3](#save-step-git) 前跑 `bash ApiRelay/scripts/selfcheck.sh`；红线失败 MUST NOT push。改了代码的收尾四问仍要回答（[`.cursor/rules/implementation-closeout.mdc`](../.cursor/rules/implementation-closeout.mdc)），不要用「已经上传」代替。纯说明改动按 [`12`](./12-通用格式要求.md) 验收链接与目录即可。

<h3 id="save-step-zl01">§1.2 · 同步被碰到的本夹页面</h3>

按路由表，**有改才动**；没碰到的页 MUST NOT 重写。本夹继续当路牌，不把 FR、模型字段、hash 再抄一份。

| 这次实际改了什么 | 才去动哪一页 |
|---|---|
| 源码文件增删 / 搬家 | [`02`](./02-代码地图.md) |
| 路径、CloudKit、不可逆约束 | [`03`](./03-路径红线.md) |
| 需求 / 阶段 / 架构决策 | 改 `ApiRelay/specs/` 或宪法（须用户确认）；[`04`](./04-设计与规格.md) 只加入口 |
| 计划 / 开发 / 上传步骤 | [`07`](./07-计划流程.md) / [`08`](./08-开发流程.md) / 本页 |
| 这段对话有进展 | 按 [`11`](./11-AI对话相关格式要求.md) 更新 [`10`](./10-AI对话相关记录.md)（协议与单独说「更新 10」相同） |
| 铁律触发或含义变了 | [`06`](./06-AI铁律清单.md) 表内一行 |
| 每一次真正 push | [`BRANCHES.md`](../ApiRelay/specs/playbooks/BRANCHES.md) + [`13`](./13-上传记录.md)（写法见 [§4](#upload-notes)） |

<h3 id="save-step-git">§1.3 · 再 git</h3>

1. `git status` 与 `git diff`：完成汇报用几句人话写出变化；`13` 的「解释」也写人话，不要贴 hash。用户划了范围则只暂存该范围。  
2. 备注只写两处，见 [§4](#upload-notes)。  
3. 判断走哪份 save，**不要问用户再解释一遍分支策略**：  
   - 规划或产品小阶段（对应 P0N 尚未关账）→ 该目录 `P0N-save.md`  
   - 已关账小迭代上的修 bug / 上架后热修（当前默认）→ [`热修-save.md`](../ApiRelay/specs/playbooks/热修-save.md)  
4. save 只管开分支、台账、commit、push。不要跳过 [§1.1](#save-step-align) 和 [§1.2](#save-step-zl01)。  
5. 没有可入库改动、对照与同步也无事可做 → 不空 commit。

<h3 id="save-bounds">§1.4 · 边界</h3>

- 对照范围 = 这次准备入库的 diff，不是整份 `spec` 对整仓。  
- 工作区若混有下一热修的未提交改动：只入库用户划定的范围，其余原样留在工作区带到下一分支。  
- 发现无关优化：只报告，不改。  
- `*.vsix`、`tools/` 下的安装包、`ZL03_原始素材/` 下的大文件、`DebugScratch/`、`build/`、密钥、`.env`、含真实密钥的截图不入库。  
- 未听到「上传 / 保存 / 提交」前 MUST NOT commit。  
- 默认不 push `main`、不打 tag、不 force push、不改 `MARKETING_VERSION`。

<h2 id="testflight">§3 · 用当前分支测试发布</h2>

测的是 **TestFlight 内测**，不是商店「提交以供审核」。已传到 ASC 的 **1.0.1 (5)** 无时长/卫生；**1.0.1 (6)** 是 9 月 9 日那包（时长/权益，无卫生）。构建号 6 已占用。源码现为 **9**（跳过未上传的 7）。
要测卫生与锁加固：从本线 Archive **1.0.1 (9)**。时长 JSON 两字段 **2026-09-10 已在 Production**（Deploy 差异为 0，不必再空跑）。

**手测卫生 / 时长列表 / 锁矩阵：必须装即将上传的 1.0.1 (9)。** 不要分发 Organizer 里仍标 1.0.1 (5)/(6) 的包。不要用 Xcode 播放键的 Debug 包当验收。顶部若是 **Any iOS Device (arm64)**，只能菜单 **Product → Archive**，点播放会弹「build only device」。

| 端 | 怎么打、怎么装 |
|---|---|
| **手机** | 设备选 Any iOS Device → **Product → Archive** → Organizer 里 **分发 App** → 选 App Store Connect，一路下一步到最后的「上传」或「分发」。浏览器 **构建版本上传** 页没有 Upload 按钮，只看进度。等 **1.0.1 (9)** 变成「完成」→ **TestFlight** 标签 → 内部组（如 `AP`）→ 手机 TestFlight 安装。 |
| **电脑** | 设备选 **My Mac (Mac Catalyst)**（不要光秃的 My Mac）→ 同样 **Product → Archive** → 选 **macOS** 那条再分发。电脑打开 TestFlight 装 1.0.1 (9)。 |

手测至少：没开 App 锁杀掉再进应直接进列表（不要白底灰锁）；开了锁能解锁；假密钥新增/复制；设置 → 恢复购买不崩；备份用假数据走一遍。不要用真实密钥。

测完停。**不要**点 ASC「提交以供审核」，**不要**让 Cursor 推 `main` / 打 `release/1.0.1`，除非另说一句授权。细则原稿（版本号仍写 1.0.0 的旧清单）→ [`P13-人工操作指南/06-TestFlight内测.md`](../ApiRelay/specs/playbooks/v1-key-vault/phases/P13-人工操作指南/06-TestFlight内测.md)，数字以本页 §2 为准。

<h2 id="upload-notes">§4 · 备注写什么</h2>

每次实际上传，写两处、不要只写一处：

| 写哪 | 写什么 | 不要写什么 |
|---|---|---|
| [`BRANCHES.md`](../ApiRelay/specs/playbooks/BRANCHES.md) | 该分支行的 **English → 简体中文**（权威） | 不要只改中文不改英文 |
| [`13`](./13-上传记录.md) | 日期、分支名、一句备注、一两句解释 | 不要抄 hash、不要贴整段 `BRANCHES` |

`13` 同一条热修线上可以多行（例如 `v1.13.2` 上后来又传了文档）。新行接在对应节**最末尾**。写法见 [`13` §1](./13-上传记录.md#how-to-log)。
