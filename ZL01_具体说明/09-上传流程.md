<h2 id="save-changes">§1 · 听到「上传」时按这个顺序</h2>

日常对 Cursor 说 **「上传」** 即可。下列口令走同一段，不必再念三件事，也不必再贴 `热修-save` 全文：

```text
上传
保存并上传
按热修-save 保存并上传
```

只说「保存」仅保存本地文件，不推定 Git 提交；明确说「提交」才做本地 commit，不推远程。只有说「上传 / 推送 / push」或已批准计划写明远端推送，才可 push。任何口令都不自动授权移动 `v1`、送审或改 `main`。

顺序固定为 **对照 → 同步本夹 → git**。先 push 再对照，冲突就要再传一次；先写说明再改代码，说明会写两遍。

开新小阶段（`P0N-save` → `plan.N` / `v1.N` / `v2.N`）见 [`07` §2](./07-计划流程.md#planning-steps)。走哪份 save 之前，仍先做完下面三步；不要用热修口令冒充新 Phase。

<h3 id="save-step-align">§1.1 · 对照本次 diff 与相关规格</h3>

只对**这次准备入库的 diff** 对照它们引用的 `spec.md` / `data-model.md` / 宪法 / 相关 playbook。用户划了范围（例如「只传流程文档」）则只对照该范围；工作区里留给下一热修的文件不纳入。MUST NOT 借「上传」做全仓审计或顺手重构。

| 对照结果 | 怎么处理 |
|---|---|
| 代码违反**仍生效**的规格 | 在这次上传对话里改到对齐（允许，且只改这件事） |
| 决策其实变了，要动宪法 / `spec.md` / `ROADMAP.md` | **停下来说明，等用户确认**。MUST NOT 擅自改决策文件 |
| 规格仍对，只是本夹摘要旧了 | 交给 [§1.2](#save-step-zl01) |
| 没有矛盾 | 完成汇报里写一句「对照过、无矛盾」，不要静默跳过 |

这次若留下一条看起来像正式设计、其实是权宜的路径，后面按计划推进时会把它当样板。要么改到符合仍生效的计划，要么在规格里写成**明确例外**（只此一次、不得当样板）。不要既不改、也不写。

本次为对齐改了代码（或本来就有未提交代码）：进入 [§1.3](#save-step-git) 前跑 `bash ApiRelay/scripts/selfcheck.sh`；红线失败 MUST NOT push。改了代码的收尾四问仍要回答（[`.cursor/rules/implementation-closeout.mdc`](../.cursor/rules/implementation-closeout.mdc)），不要用「已经上传」代替。纯说明改动按 [`12`](./12-通用格式要求.md) 验收链接与目录即可。

提交或上传前还要按 [`ZL00/06`](../ZL00_项目总控/06-方法迭代闭环.md) 看这次有没有方法卡壳。按新版方法建立、且授权范围包含阶段记录的标准/高风险工作包，先运行 `python3 -B ZL00_项目总控/自动化/check_method_iteration.py --record <本工作包的记录路径> --final`；不通过就修记录或实际缺陷并复验。若封闭文件清单排除了记录或索引，按 `ZL00/06` 报告精确欠项，不越界写文件；非阻塞方法欠项不机械挡住无关产品上传。历史工作包不倒填新记录，轻量任务无问题不建空记录。此项不能代替产品、真机、远端验收，也不额外产生上传授权。

<h3 id="save-step-git">§1.3 · 再 git</h3>

提交次数由批准范围和实际记账需要决定，**不固定为 A/B 两次**。内容提交与只有上传之后才知道的事实必须分开；无需后置记账时不制造空提交。闸门见 [`ZL00` 关账与发布](../ZL00_项目总控/03-关账与发布闸门.md)。

1. `git status` 与 `git diff`：用几句人话写出变化。用户划了范围则只处理该范围。  
2. 判断走哪份 save，**不要问用户再解释一遍分支策略**：  
   - 规划或产品小阶段（对应 P0N 尚未关账）→ 该目录 `P0N-save.md`  
   - 已关账小迭代上的修 bug / 上架后热修（当前默认）→ [`热修-save.md`](../ApiRelay/specs/playbooks/热修-save.md)  
   已经在正确的热修分支上（例如正在 `v1.13.8`），**不要再开一条**。  
3. **内容提交**：只按**显式路径**逐个 `git add`。禁止 `git add .`、`git add -A` 或会吞进无关文件的通配。不得预填尚未发生的 SHA、远端一致或上传成功。只推送本次明确授权的分支；失败就停止，报告已完成与未完成部分。
4. **必要的后置记账**：内容提交成功推送并核对远端后，才把实际提交 SHA、远端 SHA 和结果写进本次批准的工作包记录及确实需要同步的状态页。只显式暂存获准路径，单独提交并推送；不为记账提交本身无限追加“记录的记录”。没有后置事实需要入库时，不做第二次提交。
5. `v1` / `v2` / `v3` 等大阶段引用**默认不移动**。只有用户另外明确授权该引用与目标提交、对应关账条件满足时，才单独快进并核对远端；只授权热修分支上传，绝不自动授权移动大阶段引用。
6. 没有可入库改动、对照与同步也无事可做 → 不空 commit。

<h3 id="save-bounds">§1.4 · 边界</h3>

- 对照范围 = 这次准备入库的 diff，不是整份 `spec` 对整仓。  
- 工作区若混有下一热修的未提交改动：只入库用户划定的范围，其余原样留在工作区带到下一分支。  
- 发现无关优化：只报告，不改。  
- `*.vsix`、`tools/` 下的安装包、`ZL03_原始素材/` 下的大文件、`DebugScratch/`、`build/`、密钥、`.env`、含真实密钥的截图不入库。  
- 未听到「上传 / 保存 / 提交」前 MUST NOT commit。  
- 默认不 push `main`、不打 tag、不 force push、不改 `MARKETING_VERSION`。

<h2 id="testflight">§3 · 用当前分支测试发布</h2>

这里指 **TestFlight 内测**，不是商店「提交以供审核」。测试前分别核对本次候选的 `MARKETING_VERSION`、`CURRENT_PROJECT_VERSION`、源码提交 SHA、签名、安装来源与设备上显示的版本；旧 TestFlight 包、Xcode Debug 包和新候选不能混记为同一次验收。购买验收还要核对 Xcode StoreKit Configuration、Sandbox 账号状态和 App Store Connect 当时的价格，不凭旧截图或本页固定数字推断。

覆盖安装或重装实体设备前，先备份并核对可恢复范围；App 容器备份不等于系统钥匙串备份。若可能丢失本机数据，须有可信恢复方案或用户明确接受损失。Apple 退款页“无法连接”时只能记录失败与重试条件，真实退款、撤权和撤权后额度仍为未通过。

| 端 | 怎么打、怎么装 |
|---|---|
| **iPhone / iPad** | 用本次明确批准的候选 Archive 与分发方式安装；安装后在设备上再核对版本、构建号与数据状态。上传构建到 App Store Connect、分发 TestFlight 和覆盖真机安装分别需要相应授权。 |
| **Mac** | 选正确的 Mac Catalyst 目的地和本次候选构建；安装后核对构建身份与购买状态。系统账号密码由用户本人输入，不交给 AI。 |

手测至少：没开 App 锁杀掉再进应直接进列表（不要白底灰锁）；开了锁能解锁；假密钥新增/复制；设置 → 恢复购买不崩；备份用假数据走一遍。不要用真实密钥。

测完按证据分别标记通过、失败、延期与未测。**不要**把构建上传、TestFlight 分发、ASC「提交以供审核」、推 `main` 或打 tag 合并成一个授权。历史步骤原稿见 [`P13-人工操作指南/06-TestFlight内测.md`](../ApiRelay/specs/playbooks/v1-key-vault/phases/P13-人工操作指南/06-TestFlight内测.md)，其包号只作历史例子，当前值以实际工程和 ASC 为准。

<h2 id="upload-notes">§4 · 备注写什么</h2>

实际上传成功后才写上传结果；内容提交中不得预填“已经上传”。记录位置只取本次已批准且实际受影响的文件，不套固定四文件清单。

| 写哪 | 何时写 | 写什么 | 不要写什么 |
|---|---|---|---|
| 本次工作包上传记录 | 内容提交推送并核对后，若工作包要求 | 实际提交 SHA、远端 SHA、精确范围、未覆盖项 | 预填结果或把分支保全上传称为正式关账 |
| [`13`](./13-上传记录.md) | 本次范围要求更新中文流水账时 | 日期、分支名和已确认的上传事实 | 未发生的推送或重复整份技术报告 |
| [`10`](./10-AI对话相关记录.md) | 对话索引确实需要同步时 | 只记已确认的进展 | 虚构对话 UUID；预填阶段 9 通过 |
| [`14`](./14-项目当前状态.md) | 当前状态发生变化时 | 区分已上传事实与仍未完成的验收 | 预填远端最终一致或公开发布通过 |
| [`BRANCHES.md`](../ApiRelay/specs/playbooks/BRANCHES.md) | 分支台账纳入本次批准范围时 | 按既有格式记录实际内容 tip | 把记账提交误当内容 tip |

`13` 同一条热修线上可以多行。需要更新时，新行接在对应节**最末尾**。写法见 [`13` §1](./13-上传记录.md#how-to-log)。后置记账只记录内容上传已发生的事实，不为记账提交自身再派生尾单。

<h2 id="maintenance">§6 · 维护</h2>

- 听到「上传」的**完整正文只改本页 [§1](#save-changes)**。`热修-save.md` 只保留开分支、冻结引用和禁止项；Cursor 规则只负责触发并链到本页。三处都不要再复制提交步骤。
- 当前任务只改 [`14`](./14-项目当前状态.md)，不要在本页 §2 再抄一份「正在做什么」。  
- 关账 / 开热修 / 换测试包号：只改 [§2](#current-branch) 与 [§3](#testflight) 里的商店号/构建号，不抄 hash。  
- git 禁止事项、热修分支怎么开：改 [`热修-save.md`](../ApiRelay/specs/playbooks/热修-save.md)；分支命名改 `BRANCHES.md`。  
- 实际上传记录在内容推送成功并核对后按 [§4](#upload-notes) 更新；不要在 git 之前假装已经 push。
