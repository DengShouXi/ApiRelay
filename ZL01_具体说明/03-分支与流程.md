## 一、你只需要记住的一句话

改完东西，对 Cursor 说：

```
按热修-save 保存并上传
```

它会自己判断该开哪条分支、写台账、commit、push。**你不用自己起分支名、不用自己写台账。**

这句话对应的文件是
[`../ApiRelay/specs/playbooks/热修-save.md`](../ApiRelay/specs/playbooks/热修-save.md)。
Stage 1 已经上架，所以现在默认走的就是这一份（「上架后热修」），不是新的 P0N 阶段。

## 二、现在在哪（摘要）

Stage 1 已发布到 App Store，商店版本 **1.0.0**，对应 tag `release/1.0.0`。
之后所有修 bug 都在**热修线**上做，商店版本号先不动。

```text
release/1.0.0 (tag)  ← 上架的就是这一包，永远不动
main                 ← 停在 1.0.0，除非另行授权才前进
v1.13                ← 已关账，冻住
  └─ v1.13.1         ← 已关账，冻住
       └─ v1.13.2    ← 现在在这条上干活
v1                   ← 大阶段 tip，跟着最新热修往前走
```

具体每条分支做了什么、tip 是哪个 commit，看
[`BRANCHES.md`](../ApiRelay/specs/playbooks/BRANCHES.md) 的「当前分支」一节。
**本页不抄 commit hash**，抄了迟早不一致。

## 三、三个「版本号」不是一回事

这是最容易混的地方，所以在这里说清楚。完整解释见 `BRANCHES.md`「分支 vs tag」。

| 名字 | 例子 | 是什么 | 会往前走吗 |
|---|---|---|---|
| Git 分支 | `v1.13.2` | 现在做到哪 | 会 |
| Git tag | `release/1.0.0` | 当时上架的是哪一包 | **不会**，是钉死的名牌 |
| 商店版本 | `1.0.0` | 用户在 App Store 看到的号 | 只在送审时才改 |

由此来的三条硬规矩：

- `release/*` **只能是 tag，不能建成分支**。已经有 `release/1.0.0` 这个 tag 了，
  再建同名分支会撞车。
- 修 bug **不要**提交到叫 `release/1.0.1` 的地方。Git 上开 `v1.13.3`，
  商店号 `1.0.1` 是下次真送审时才改。
- **不要**在已关账的 `v1.13` / `v1.13.1` 上继续提交，那会盖掉冻结的里程碑。

## 五、为什么这些文件不搬到本文件夹来

因为它们的路径**被写死在配置里**，搬了就断：

- `.cursor/rules/versioning-release.mdc` 写死了 `BRANCHES.md` 和 `热修-save.md` 的路径，
  AI 每次对话都按那个路径去找。
- 宪法引用了 `重要说明/索引.md` 两次。
- spec-kit 把 `specs/` 这个路径写死在自己代码里。

完整清单见 [`02-路径红线.md`](./02-路径红线.md)。
**要让它们更好找，办法是加链接（就像本页），不是搬文件。**
