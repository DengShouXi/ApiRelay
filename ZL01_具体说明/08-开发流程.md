<h2 id="before-coding">§1 · 动手前先确认</h2>

| 情况 | 先做什么 |
|---|---|
| 修 bug / 改文案 / 改本夹说明 | 核对目标工作树与分支归属（见 [`09` §2](./09-上传流程.md#current-branch)），再按任务范围修改 |
| 需求或阶段范围变了 | 先走 [`07`](./07-计划流程.md)，再动手 |
| 一项任务涉及多处 | 先明确同一个目标和必要依赖；无关优化另记，必要的跨模块修改可以一并完成 → [`06`](./06-AI铁律清单.md) |
| 高风险或需要两个/多个 AI、多个编辑器接力 | 按 [`ZL00/04`](../ZL00_项目总控/04-双AI协作与独立审计.md) 选择检查强度和交接方式；仅协作意图只读路由，具体任务可按已批准连续范围执行；同一工作区同时只能有一个写入者 |
| 机器侧整改已收、不知下一步 | 先看带核实日期的 [`14`](./14-项目当前状态.md) 和对应工作包；[`10` §5](./10-AI对话相关记录.md#五目前未完成) 只供历史追溯，不能直接执行旧推荐顺序或旧构建号；测试发布再按 [`09` §3](./09-上传流程.md#testflight) 核对现场 |

不要假定每个窗口都在同一热修线。保存／提交／上传口令只写在 [`09`](./09-上传流程.md)，当前核实快照见 [`14`](./14-项目当前状态.md)；操作前仍须读取实时 Git。

<h2 id="specs-or-archive">§3 · 规格还是研发档案</h2>

| 你在干什么 | 写在哪 |
|---|---|
| 改需求 / 阶段范围 / 架构 | **只改 A**：`ApiRelay/specs/`、宪法。地图见 [`04`](./04-设计与规格.md)、顺序见 [`07`](./07-计划流程.md) |
| 事故复盘、验证地基、止血类整改 | **写在 B**：[`ZL02_研发档案/`](../ZL02_研发档案/) |
| 平常推进功能或修 bug | 代码在 `ApiRelay/ApiRelay/`；收工走 [`09`](./09-上传流程.md) |

例：[`第一次-测试删除主密码/00-总览.md`](../ZL02_研发档案/第一阶段-密钥库/事故复盘/第一次-测试删除主密码/00-总览.md)（战略顺序 H1→H2→…→99；**机器侧已验收通过**）。  
改需求仍回 A，不要把 FR 抄进 ZL02。

<h2 id="done-when">§4 · 做到哪算能收</h2>

1. 改完代码默认跑：

```bash
bash ApiRelay/scripts/selfcheck.sh
```

2. 方案与收尾：[`H1-验证地基.md`](../ZL02_研发档案/第一阶段-密钥库/事故复盘/第一次-测试删除主密码/H1-验证地基.md)；Cursor 斜杠命令 `/closeout`。
3. 说明夹改完：按 [`12`](./12-通用格式要求.md) 验收链接与目录。只有对话索引确实需要同步时，才按 [`11`](./11-AI对话相关格式要求.md) 更新 [`10`](./10-AI对话相关记录.md)。
4. 若用户要求本地提交或上传，分别按 [`09` §1](./09-上传流程.md#save-changes) 的授权范围处理；“保存”不是自动 push。本页不复制 Git 步骤。
