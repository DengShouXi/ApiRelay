## 一、主要矛盾

**产出速度远远超过验证能力。**

事实：5 个工作日、60 次提交、从 0 到 15503 行生产代码并准备上架。写的速度是 AI 的速度，
验的速度还是人眼的速度。

这对矛盾里，**主要方面在「验证」这一侧**——速度不该降，那是这个项目最大的优势。
所以整改的总方针只有一句：

> **把验证能力提上来，追上产出速度。**

### 派生出来的毛病，以及它们的共同点

| 表面现象 | 数据 |
|---|---|
| 界面层几乎无法自动测试 | 界面 9018 行占全部生产代码 58%，147 个测试**全部**打在业务/数据层 |
| 单个文件过大 | `VaultHomeView.swift` 4313 行 = 全部生产代码的 28%；`SettingsView.swift` 1349 行 |
| 接口定了没接上 | 15 个 `XxxServing` 协议，服务之间**一半焊死一半认接口** |
| 测试只能用真零件 | 事故当天之前，全项目只有 0 个测试替身 |
| 错误被吞掉 | 44 处 `try?`，其中 25 处在界面层 |
| 环境判断散落 | `XCTestConfigurationFilePath` 在 3 个文件里独立判断 4 次 |

**共同点（这才是机制）**：上面每一条，**都不影响 App 能不能跑起来**。
所以在「跑起来就算做完」的节奏里，它们永远不会被发现，只会累积。

反过来说，凡是**影响跑起来**的问题，这个项目里几乎没有——三层分层守得干干净净，
因为破坏分层会编译不过。

> **结论：编译器管得住的地方一点问题没有，编译器管不住的地方全是问题。**
> 所以整改的方向不是「写得更小心」，是**把更多东西挪到机器管得住的那一侧**。

### 明确不是矛盾的东西

**架构不需要重新设计。** 三层（UI / Business / Data）分得清楚、接口定义完整、模块边界明确，
够用到 Stage 3。

因此本次整改 **MUST NOT** 做下列任何一件：

- 换架构（TCA / VIPER / Clean Architecture 等）
- 拆成 Swift Package 模块
- 专门开一次大重构去拆 `VaultHomeView.swift`
- 给 Stage 2 / Stage 3 现在补失败预案（需求还会变，白写）

## 二、战略四步

```
H1 地基 ──→ H2 止血 ──→ H3a 改认接口 ──→ H3b 配假零件 ──→ H3c 救活预览
                                                              │
                                                              ↓
                                                          H4 补失败预案
                                                              │
                                                              ↓
                                                          99 总验收
```

### H1 · 地基：把验证机制装上

不动一行业务代码，只改模板、规则、脚本。装完之后，「不影响跑起来所以没人管」的问题
会变成「过不了自检」。

**为什么排第一**：后面每一步都要靠它兜着。没有 H2 那道硬保险，H3a 改 8 个文件的过程中
很可能又碰到真实用户数据——**这不是假设，2026-08-22 刚发生过**。

### H2 · 止血：补上还在漏的口子

环境判断收到一处；测试碰到生产资源当场崩（钥匙串那条已修，**本机设置那条还开着**）；
清警告并设成有新警告就编不过。

### H3 · 降本：解决「改界面老要反复试错」

- **H3a** 把 7 个服务 + 组装根里焊死的依赖改成认接口（改已有文件）
- **H3b** 配齐约 15 个假零件（纯新增文件）
- **H3c** 给两个主界面加 Xcode 预览——**改一行立刻看到，不用编译不用跑模拟器**

### H4 · 清债：补失败预案并填洞

通读 Stage 1 已实现部分的 71 条需求，找出「有前提但前提没了没人管」的地方，补预案再填洞。

**只补 Stage 1 已实现的部分。**

### 不排期、持续做的一件

**界面逻辑往可测模型里挪、大文件拆小——改到哪做到哪，不专门开。**

理由：拆界面风险最高（视觉走样、状态丢失，编译器和测试都发现不了），
而现在没有界面测试兜底，拆的过程只能肉眼一页页看——恰恰是最该摆脱的那件事。
这条会写进 `.cursor/rules`，由 H1 负责。

## 三、模型分工表

> **原则**：需要跨文件推理、需要判断「该改成什么样」、碰密钥与用户数据 → 贵模型。
> 改哪里改成什么已经写死、纯新建文件、照模板抄 → 便宜模型。

| 步骤 | 用哪个 | 为什么 |
|---|---|---|
| `H1-验证地基` | 便宜 | 全是新建文档与脚本，内容已在提示词里写死，不需要判断 |
| `H2-止血` | 便宜 | 改动点精确到行；验证方式是「故意触发，应该崩」 |
| **`H3a-服务改认接口`** | **贵** | 跨 8 个文件；协议缺方法要现场判断；编不过时要会分析原因 |
| `H3b-配假零件` | 便宜 | 约 15 个新文件，照模板抄，每个的方法清单已给出 |
| `H3c-救活预览` | 便宜 | 纯新增代码；验证方式是「预览能不能显示」 |
| **`H4-补失败预案`** | **贵** | 通读 71 条需求找漏兜底的地方，纯判断 |
| **`99-总验收`** | **贵** | 要判断「改**对**了没有」，不是「改**完**了没有」 |

### 升级规则（省钱的关键）

**便宜模型在同一步连续两次验证不过 → 停手，换贵模型。**

不要让它继续试。便宜模型自己「修复」会越修越坏，返工的总成本远高于一开始就用贵模型。

## 四、通用停手条件

出现下列任何一条，**立刻停手，不要继续下一步**：

1. 任何一步的验证命令没通过。
2. 需要改动本步骤「不许碰的文件」清单里的文件才能继续。
3. 提示词里写的行号 / 内容与实际文件对不上（说明文件已被改过，提示词过期了）。
4. 出现与密钥、主密码、用户数据相关的删除或重置操作，而当前步骤没写明要做这件事。
5. 连续两次尝试仍未通过验证。

停手时**必须**把错误原文完整贴出来，**不要**自行改方案、不要跳过、不要「先注释掉再说」。

## 附：一个已知的环境事实（影响 H1 挂钩点）

`ApiRelay/.specify/integration.json` 显示，本项目的 spec-kit **只安装了 Copilot 集成**
（`installed_integrations: ["copilot"]`，skills 模式），命令实体在 `.github/agents/`、
`.github/prompts/`、`.github/skills/`——这些是 VS Code + Copilot 的位置。

而实际开发在 **Cursor** 里进行。Cursor 的原生挂钩点是：

- `.cursor/rules/*.mdc`——**每次对话自动加载，已验证生效**（最可靠）
- `.cursor/commands/*.md`——斜杠命令，**该目录目前不存在，需要创建**

因此 `H1` 会**两边都装**：`.cursor/` 一套（Cursor 用），`.github/agents/` 一套（Copilot 用），
外加与客户端无关的 `spec-template.md`。无论用哪个客户端，至少有一道闸生效。
