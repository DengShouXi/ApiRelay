# 方法体系单 AI 适配与逐阶段改进：审计及整改记录

日期：2026-10-09。实施位置：`v1.13.12` 当前工作树。性质：项目治理方法整改；不改变 App 产品语义，不移动 `v1`、`main` 或 tag。原工作树已有 Xcode 工程、AppIcon、Xcode Cloud 和 UI 设计差异，均保留且不纳入本次方法修改。本报告 §1–5 记录最初仅本地整改时的事实；后续复核与上传事实另见 §6–7，不倒填早期结果。

## 1. 使用对象与触发原因

“双 AI 协作”用于**两个实际 AI 实例**分工或交叉审计，不用于一个 AI 操作多个工具，也不用于仅讨论双 AI 方法。此前 `ZL00/04` 把跨目录、权威冲突、上传和安全高风险写在触发列表；`ZL01/08` 又把“多目录、高风险”直接路由到 `04`，导致单 AI 复杂任务误入九阶段。全局 `multi-ai-collaboration` 技能本身限定用户的协作意图，不是这次误触发的主要来源。

本轮增加 `ZL00/05` 作为单 AI 通用流程，`04` 只保留真实多 AI 分工；AGENTS、Cursor 和 ZL01 入口同步按实际参与人数路由。单 AI 的自查明确不得叫独立审计。
即使确有两个 AI，标准风险的短任务也可用紧凑交接；九阶段契约与检查器只用于明确选择的长周期或高风险完整包，不再由“跨文件”三个字自动强制生成九份阶段提示词。

## 3. 冲突与实际情境

| 旧冲突 | 修订后的判定 |
| --- | --- |
| 单 AI 高风险/跨目录任务被强制拉入双 AI 九阶段 | 风险决定验证深度，参与人数决定是否启用 `04`；单 AI 走 `05` |
| 每换阶段重新问授权，已有连续授权失效 | 记录目标、文件/系统、操作、引用、前置条件和停止点；范围内连续执行，不因阶段号重复索权 |
| 上传固定 A/B、四文件记账并自动移动 `v1` | 内容提交与事后事实分离；确需后置记录才另提交；仅推授权分支，`v1` 默认不动 |
| 未登记、无关的脏 worktree 导致检查器退出 4 | 只提示其路径；明确登记为本任务输入的只读树仍严格检查，保留隔离保护 |
| 测试包号和当前状态写死在长期流程 | 上传页改为现场核对构建身份；`14` 明示本轮工作树与旧快照边界 |
| “方法观察”只留下候选，不自动改善 | 每个实质阶段按 `05` 做健康检查；范围内低风险问题当场修正并验证，结构性问题记录证据和回归用例 |

保留不变：用户决定权、产品宪法和规格权威、密钥/数据安全、单写入者、真实测试欠项不得冒充通过、明确提交上传授权、不得 force push、历史证据不可倒填。Apple 退款页“无法连接”属于外部阻塞；真实退款及撤权仍未通过，方法修订不能把它变成通过。

## 4. 验证与剩余边界

- 多 AI 检查器标准库测试：87 项通过，包含新增的无关脏 worktree 只提示、空上传跟踪引用拒绝、未实例化来源/风险拒绝、仅授权热修分支追踪时不要求移动 `v1`。
- 项目自检红线通过；治理入口只读一致性检查通过；`git diff --check` 通过。远端 SHA 实时核验是将来实际上传时的操作，本轮未上传，因此没有伪造远端验证结果。
- 本轮是单 AI 实施与自查，**不是第二 AI 独立验收**；任何需要独立审计的具体发布任务仍须另行取得真实审计证据。
- 当前修改仅在本地 `v1.13.12` 工作树，未提交、未推送；`v1.13.11` 保全上传与本轮方法整改不是同一事件。

代码收尾四问：

1. 外部资源：本轮 Python 检查器只读文件与 Git；测试用临时仓库隔离，不访问 App Keychain、SwiftData、CloudKit、StoreKit 或真实设备数据。
2. 失败路径：未实例化的来源/风险、空上传跟踪引用和已登记只读树漂移会明确失败；无关 worktree 只提示。新治理入口检查器对输入缺失/格式错误返回非零并报告，不擅自修复。
3. 接缝：未新增 App protocol；Git/文件系统检查由标准库临时仓库夹具覆盖，远端实时状态须留给实际上传后的独立读取。
4. 文件粒度：`check_multi_ai_workflow.py` 原本已超过 400 行，本轮仅做局部修改和回归，不顺便重构；App 大文件报告保留给对应产品任务处理。

方法观察：本轮发现项目本地路由扩大了全局协作触发、旧上传规则在多个现行入口残留，已按同一目标修正并加入对应回归；未改变产品需求或把外部退款故障伪装为方法测试通过。

## 6. 上传前按八项标准再次复核与返修

这次复核没有把首次 106 项测试通过直接当成最终结论。按“现场 → 自动迭代断点 → 架构 → 闭环 → 入口 → 工具 → 旧问题 → 总验收”逐项回查，发现四处会让下次任务再次卡住的矛盾，均已回到对应步骤修正，而非重做整套计划：

| 问题 | 根因与修复 | 反例复验 |
| --- | --- | --- |
| `MI-20261009-02` | 封闭文件白名单可能不含统一索引，但旧规则要求强制写索引；允许非阻塞方法问题明确记为待授权补索引，或在记录也被排除时于允许的报告/答复交代欠项，不阻塞无关产品上传；安全/正确性阻塞不借此放行 | `pending_scope` 的非阻塞夹具通过且显示待办；阻塞夹具失败 |
| `MI-20261009-03` | 双 AI 方法一处允许连续计划，另一处还要求逐阶段重新点名；统一为明确点名或此前批准计划覆盖目标、范围、操作及停止点即可继续 | 故意加回旧点名句，入口检查器失败 |
| `MI-20261009-04` | `BRANCHES.md` 的旧快照自称当前并强制每次 save 更新；标为 2026-09-24 历史快照，当前状态只看 `ZL01/14`，是否更新按范围和事实 | 故意加回每次必改句，入口检查器失败 |
| `MI-20261009-05` | `ZL01/00`、`09` 和 `13` 仍强制改双台账、每段对话改 `10`，还把历史 BRANCHES 当实时 tip 权威；改为只同步获准且受影响页面，当前 tip 和远端 SHA 以实时 Git 核对 | 四种旧入口句分别加回，入口检查器失败 |
