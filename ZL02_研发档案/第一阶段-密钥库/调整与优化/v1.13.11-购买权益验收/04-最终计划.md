### 一、总判断

当前代码不是“购买逻辑整体失效”。它已经具备正确的主骨架：StoreKit 2 已验签交易是唯一授权事实，本机 snapshot 不授予权益；购买返回与 `Transaction.updates` 汇入同一入口；设置页、付费墙和额度显示共享一个 `EntitlementStore`；普通新增、回收站恢复、备份导入都经过同一配额闸门；普通 App 默认拒绝 `.xcode` 假交易；退款只撤销后续超额写入，不删除用户已有密钥。

剩余问题分成三类，不能混写：

1. **确定存在的验收阻塞**：当前成熟代码快照尚未在真实 Sandbox 重新完成购买、付款取消、退款撤权和 Mac 付款；旧真机证据早于 `5654cb4` 成熟实现，只能作历史线索，不能替代当前 HEAD 验收。iOS 26.5 的三项本地 StoreKit 测试仍全部 `notEntitled`。
2. **代码层的系统性薄弱点**：StoreKit 原生类型仍穿过业务协议；协议默认实现会在假对象漏实现时偷偷创建真实 `LiveStoreKitClient`；生产 `ProductView` 与自定义 `productInfo()` 各自拉一次同一商品；未验签原因和商店错误被压成泛化字符串；权益变化只广播“变了”而不携带代次/原因；App 环境被进程内缓存，测试环境切换后只能靠重启兜底。
3. **Apple 环境限制或外部状态**：Sandbox 购买历史清除可能延迟；退款表单此前两机均“无法连接”；Sandbox 能进入 Ask to Buy 待批准，但 Apple 明确不支持在 Sandbox 里批准/拒绝；工作包检查器当前还被两个外部状态阻断：契约中的根工作树冻结身份是 `v1.13.9 @ 25fe006`，实际已变为 `v1.15 @ 47626b1`；另出现契约外 `v1.14 @ f80b1a6` 工作树。这些不能用改权益判定、放宽验签或改检查器来掩盖。

所以建议是：**不重写 StoreKit 核心，也不引入第三方购买后台；先消除边界重复和测试泄漏，再按 Apple 支持矩阵完成分层验收。** “一劳永逸”在这里应定义为：状态来源唯一、异常可诊断、每种场景有确定归属的测试层、以后改代码会被自动回归拦住；不能承诺 Apple Sandbox 或退款服务永不故障。

### 三、参考的成熟项目与官方实现

1. [Apple / sample-backyard-birds，固定 SHA `1843d565`](https://github.com/apple/sample-backyard-birds/tree/1843d5655bf884b501e2889ad9862ec58978fdbe)：采用 StoreKit `ProductView`/`SubscriptionStoreView` 负责原生商品展示与付款，不再叠加第二个自定义购买发起器。当前项目采用 `ProductView` 的方向来自这里；下一步应继续消除生产环境的双商品加载状态。
2. [RevenueCat / purchases-ios，固定 SHA `a2465d4`](https://github.com/RevenueCat/purchases-ios/tree/a2465d4abaea95560d48bfb14ebcd4dbf8304500)：参考其 StoreKit 2 listener、购买结果分类、交易抽象和可注入依赖；采用“统一处理 verified/cancelled/pending、监听外部交易、测试替换边界”的思想，不引入 RevenueCat 服务、账号体系或后台。
3. [Apple：StoreKit views](https://developer.apple.com/documentation/storekit/storekit-views) 与 [ProductView](https://developer.apple.com/documentation/storekit/productview)：确认原生视图可自行加载本地化商品信息并管理付款 UI。生产界面应只有一个付款拥有者。
4. [Apple：`Transaction.currentEntitlements`](https://developer.apple.com/documentation/storekit/transaction/currententitlements)：非消耗型买断应从当前权益读取；退款或撤销的商品不会继续出现在当前权益中。支持本项目“StoreKit 是真相、本地 snapshot 只观测”的不变量。
5. [Apple：`Transaction.updates`](https://developer.apple.com/documentation/storekit/transaction/updates)：同机购买结果从 `Product.PurchaseResult` 返回；Ask to Buy、App Store 外部购买、其他设备完成的交易经 `updates` 到达。支持两入口汇入同一验证器，而不是只依赖一种回调。
6. [Apple：`AppStore.sync()`](https://developer.apple.com/documentation/storekit/appstore/sync%28%29)：只应响应用户显式“恢复购买”；正常新设备会自动取得交易，不需要用户先点恢复。由此纠正“必须看到免费→点恢复→已购才算恢复”的旧验收口径。
7. [Apple：Xcode 与 Sandbox 测试能力矩阵](https://developer.apple.com/documentation/storekit/testing-at-all-stages-of-development-with-xcode-and-the-sandbox)：购买、恢复、退款、被中断购买两边均可测；Sandbox 只能发起 Ask to Buy 待批准，**不能批准/拒绝**，批准/拒绝必须放到 Xcode StoreKit 测试。
8. [Apple：Xcode StoreKit transaction manager](https://developer.apple.com/documentation/xcode/testing-in-app-purchases-with-storekit-transaction-manager-in-code)：可批准/拒绝 Ask to Buy、退款、解决被中断购买，并可模拟其他设备完成交易。
9. [Apple：Sandbox 账号设置](https://developer.apple.com/help/app-store-connect/test-in-app-purchases/manage-sandbox-apple-account-settings)：官方支持为 tester 开启 interrupted purchases 和清除购买历史；清除历史多时可能需要传播时间，不能把按钮返回成功等同于两台设备已变免费。
10. [Apple：测试退款请求](https://developer.apple.com/documentation/storekit/testing-refund-requests)：Sandbox 提交普通退款理由会自动批准，输入 `DECLINE` 可测拒绝；批准后交易应带 `revocationDate`/`revocationReason`。此前“无法连接”只是当前外部阻塞，不是预期成功结果。

另检查了 Apple 2026 新样例“Implementing a store in your app using the StoreKit API”，但其文档明确标注为 beta/preliminary，不作为本阶段定案依据。未采用停止维护的 SwiftyStoreKit，也不建议为一个非消耗型商品引入 RevenueCat 后台。

### 四、建议的最终修改计划

#### 波次 A：先把生产边界和测试边界做成单一来源

1. 生产购买只保留一个商品对象和一个付款拥有者。建议由 StoreKit 展示适配层加载一次 `Product`，同一实例交给预加载商品形式的 `ProductView(product)`；业务权益层不再维护另一份“商品已加载”真相。DEBUG UI fixture 可保留自定义按钮，但必须编译期隔离并在 Release 二进制检查中证明不存在。
2. 在 StoreKit 适配器内把原生结果立即转换成项目内部的 `StorePurchaseOutcome`；从 `EntitlementServing` 删除 `Product.PurchaseResult`。取消、pending、verified、unverified、商品不可用、网络/商店错误使用稳定枚举，不再靠字符串 reason 驱动 UI。
3. 删除 `EntitlementServing` 会偷偷创建 `LiveStoreKitClient` 的默认 `productInfo()`；所有 fake/stub 显式实现所需能力，编译器负责发现遗漏，任何非 StoreKit 测试都不得碰真实商店。
4. 把权益变化从“空 NotificationCenter 广播”收口为带 `revision + source + outcome` 的类型化事件流；UI 仍只展示 checking/free/owned/unavailable，但诊断能区分购买返回、外部批准、退款、前台复核、显式 sync 和查询失败。
5. 保留 verified-only、产品 ID、撤销和普通 App 拒绝 `.xcode` 的判定；保留短期内存衔接，禁止落盘授权。对 `cachedAppEnvironment` 增加明确失效策略或取消缓存，避免同一测试进程切换环境后必须靠重启纠偏。
6. 记录匿名、可删的结构化诊断：构建 SHA/号、设备类型、事件源、交易环境、产品 ID、交易 ID 的不可逆短摘要、是否 verified/revoked、错误类别和时间。不得记录邮箱、JWS、Apple 凭据或密钥内容。

#### 波次 B：先修 iOS 26.5 自动测试隔离，不碰授权语义

1. 建立独立 StoreKit 测试 scheme/test plan：一种方式由 Test Action 注入 `.storekit`，另一种由 `SKTestSession(contentsOf:)` 自己管理；同一进程不叠加两个配置所有者。测试串行、每例前后清交易，并记录 runtime、SDK、Xcode 和配置来源。
2. 在 iOS 18 与 iOS 26.5 分别跑最小探针：仅载入配置、仅买商品、读取 `allTransactions`、读取 `currentEntitlements`、经适配器读取、经权益服务读取。由最早失败点判定是配置、StoreKitTest runtime、适配器还是授权策略，不在症状末端猜根因。
3. 若 26.5 仍在 `SKTestSession.buyProduct` 之前/当下返回 `notEntitled`，保留为工具链阻塞并附最小复现；不得改为跳过、允许普通 App 接受 `.xcode` 或信任 snapshot。若隔离后通过，再把三项纳入每次购买阶段闸门。

#### 波次 C：建立永久回归矩阵

1. 纯状态机测试：成功、付款取消、pending、批准更新、拒绝无更新、未验签、错误、重复交易、乱序、退款先后顺序、跨设备更新、恢复期间更新、短衔接到期。
2. 真实业务闸门测试：免费第 4 把失败；购买后立即第 4 把成功；退款后已有 4 把保留但第 5 把失败；普通新增、回收站恢复、备份导入使用同一组表驱动用例。
3. Xcode 原生 StoreKit 测试：用 transaction manager 完成 Ask to Buy 的 pending→批准和 pending→拒绝、退款、被中断交易解决、模拟另一设备交易。这里才是 Apple 官方支持的“待批准完整闭环”。
4. UI 测试继续覆盖文案和可重试性；另加一组不走自定义 DEBUG 购买按钮的原生 `ProductView` 冒烟验收，证明生产回调实际接上。不得用 fixture 14/14 替代原生付款链路。
5. 静态闸门检查：Run Action 无 `.storekit`、Test Action/专用 plan 才有；Release 无 DEBUG fixture/测试退款入口/模拟 Ask to Buy 标记；产品 ID 唯一且与 App Store Connect 一致。

#### 波次 D：按 Apple 能力边界完成当前 HEAD 的真实验收

先产生一个来自最终候选 SHA 的开发签名构建，Run StoreKit Configuration 必须为 None。每项证据记录 SHA、构建号、设备/系统、tester 匿名代号、开始/结束时间、交易环境和最终权益；旧构建证据不与当前候选混用。

1. **免费基线**：清除 tester 历史后，必须等 iPhone/iPad 的 `currentEntitlements` 都为空才开始；若 Apple 侧长期不传播，建议创建一个只用于免费/取消/首购的全新 tester，而不是继续在污染账号上猜。不得删用户 App 数据来冒充商店清空。
2. **付款取消**：非消耗型商品没有“订阅取消”。这里验系统付款页点取消后仍为 free、无错误恐吓、同页可再次购买、没有交易和第 4 把授权。
3. **成功购买**：同一免费 tester 在 iPhone 通过生产 `ProductView` 完成 Sandbox 买断；验 `.sandbox + verified + 未撤销`、UI owned、立即新增第 4 把、重启后仍 owned。
4. **跨设备**：iPad 在未手动恢复前启动同一最终构建，应自动读到同一非消耗型权益；这才符合 Apple 的主动恢复模型。再点一次“恢复购买”，验 `AppStore.sync()` 完成且权益不丢、反馈可见。无需也不应强求先显示一个错误的免费态。
5. **待批准**：完整的 pending→批准/拒绝在 Xcode transaction manager 验收；如还要真实 Sandbox 旁证，只要求发起后进入 pending，因为 Apple 官方不支持在 Sandbox 里批准/拒绝。不要把这个限制记成 App 缺陷。
6. **退款批准**：如果产品决定允许正式设置页提供“请求退款”，使用 Apple 原生 `refundRequestSheet`；若不增加正式入口，则使用专用验收构建，但必须编译期隔离并在最终候选删除。Sandbox 选择普通理由提交，等待 `revocationDate` 更新；验两台设备回到 free、现有 4 把不删除、第 5 把拒绝、重启后仍 free。
7. **退款拒绝**：Sandbox 退款原因选 Other 并输入 Apple 规定的 `DECLINE`，验仍为 owned。它与退款批准分开留证，防止把“表单打开”误写成退款通过。
8. **Mac**：至少在当前候选上验证 ProductView 商品/价格、付款取消、owned 状态和恢复；若用独立 tester 完成 Mac 首购，再在 iOS 验同一通用购买。仅有 Mac/Catalyst 编译通过不算付款验收。

其中“是否把请求退款入口作为正式产品功能”是新的 UI/产品决定，实施前需用户明确确认；它不影响 App 必须自动处理外部退款撤权。

#### 波次 E：回归、独立验收、上传与关账

1. 完整单元、iPhone/iPad 全套 UI、原生 StoreKit 两个目标 runtime、Mac/Catalyst Release、selfcheck、工作包检查器、`git diff --check` 全部重新跑在最终候选 SHA；任何失败不得被旧 639/639 覆盖。
2. 先裁决契约外 `v1.14 @ f80b1a6`，以及根工作树从契约冻结的 `v1.13.9 @ 25fe006` 变为 `v1.15 @ 47626b1` 的归属和保全方式；检查器退出 4 时，即使购买全绿也不得进入关账。不得由本购买任务自行删除、切分支或覆盖这些外部工作树。
3. 按工作包阶段 5/7 做另一角色独立审计；不能由实现者自我签字。审计要重新读取代码、结果包、真机证据和保护 refs，而不是只看实施报告。
4. 只有最新验收通过，才提交最终收尾；按用户另行有效授权推送 `v1.13.11`，读取远端 SHA，核对本地/远端一致和保护 refs 未动，再写阶段 9 远端复核并关账。不得推进 `v1`、`main`、tag、Archive、TestFlight 或审核，除非另有授权。

### 五、最终完成标准

只有以下条件同时成立才建议宣布“购买权益阶段完成”：

- 当前最终 SHA 的生产 `ProductView` 已真实完成成功购买与付款取消；
- pending 的进入、批准、拒绝按 Apple 支持矩阵完成，拒绝没有被伪造成一笔交易；
- 新设备自动取得权益，显式恢复按钮可完成且反馈可见；
- Sandbox 退款批准产生真实撤权，退款拒绝保持权益；
- iOS/iPadOS/Mac 目标结果与自动回归相互一致；
- 免费配额的所有激活入口无绕过，退款不删旧数据；
- 没有 Release 测试开关、`.xcode` 假交易放行、凭据/JWS 日志或本地永久授权；
- 工作包检查器、独立验收、提交推送和远端复核都通过。

在这些条件满足前，准确结论仍是：**成熟实现检查点已保存，但购买权益阶段未关账。**

方法观察：本轮发现旧真机证据与当前成熟代码快照容易被误合并，以及“Sandbox 必须批准 Ask to Buy”“恢复必须出现免费→已购”两条验收口径与 Apple 官方能力不一致。计划已改为按证据 SHA 和测试环境分层；未发现需要修改项目通用治理方法的新增问题。
