# 密码与身份验证整体架构审计与加固

> 日期：2026-09-24
> 范围：设备验证、应用密码、组合档、会话锁、明文取用、自动锁、切换器遮挡、剪贴板、Keychain、同步安全偏好、备份导入与全量清除。
> 状态：本轮现行技术结论；不是旧阶段提示词的续执行入口。

## 1. 结论

现有分层方向基本合理，不应推倒重写：UI 不直连 Keychain，`RevealGate`、`MasterPasswordService`、`KeyVaultService`、`AppPrivacyController` 和数据仓已有责任分层。过去开发“改一处、另一处又坏”的核心不是 SwiftUI 或 `LocalAuthentication` 本身不可用，而是认证结果、会话有效期、生命周期、明文复用和安全偏好分属多个对象，过去没有一个统一的、可撤销的授权事务贯穿它们。

同时必须准确定义保护强度：现行 V1 是正常 Apple 设备上的“应用隐私门闩 + Keychain 存储”，不是把每一次解密都与 Secure Enclave 密钥操作绑定的高保障密码管理器架构。这不影响当前产品按既定威胁模型稳定运行，但不能对外声称“系统级不可绕过”。

## 2. 成熟架构的六层边界

| 层 | 责任 | 本项目现行落点 |
| --- | --- | --- |
| 策略层 | 定义四档、强制验证、降级前验证；不直接弹系统框 | `RevealPolicy`、`SecurityPolicyChange`、`PreferencesService` |
| 认证请求层 | 一次请求一个 owner/id/context；取消、超时和错误分类 | `AuthenticationRequestCoordinator`、`RevealGate` |
| 会话与隐私层 | 前后台、失焦、自动锁、遮挡、授权换代 | `AppPrivacyController`、`AppLockSession`、`SessionLockBox` |
| 凭据层 | 设备认证交给 Apple；应用密码只存验证材料；失败持久限速 | `RevealGate`、`MasterPasswordService`、`KeychainStore` |
| 受保护业务层 | 敏感操作开始捕获授权，认证后和每个副作用前重验 | `KeyVaultService`、`ConsumerToolService`、`SecureBackupService`、回收站、`DataLifecycleService` |
| 存储与跨设备层 | 区分同步数据、本机材料、用户期望状态与当前设备有效能力；跨存储失败补偿与崩溃恢复，清除期间统一封口，冲突时安全失败关闭 | `KeychainStore`、`UserPreferencesRepository`、`StorageMutationGate`、`DurableCrossStoreTransactionJournal`、`DurableDataEraseJournal`、`VaultIntegrityQuarantineStore` |

## 3. 本轮发现的问题与处置

| 级别 | 问题 | 处置 |
| --- | --- | --- |
| P0 | 认证开始时未锁，但等待系统框期间已离开/锁定，旧结果仍可继续副作用 | 新增 `SessionAuthorizationLease`，绑定 `sourceID + generation`；确认离前台、锁定、安全偏好变化时正式换代；mobile resign 尚无离屏证据时先使用可逆 provisional fence，确认后才升格为正式 suspension；明文、剪贴板、删除、恢复、导入导出和清空均重验 |
| P0 | 业务层重验后到真正 `save` / Keychain / 剪贴板写入之间仍有窗口 | 引入 `PreferencesCommit`、`KeychainCommit`、`RepositoryCommit`和 `ClipboardCommit`；授权检查与同步副作用在同一最终提交接缝内完成 |
| P0 | 新建密钥时元数据与 Keychain 分属两个存储，进程崩溃可留下孤儿或“有记录无密文” | `createKey` 使用持久 WAL：`.applying` 启动回滚，`.commitDecided` 启动前滚，`.completed` 只重试清除标记；Keychain 以精确 transaction tag 证明回滚所有权，SwiftData 以 `id + createdAt` 防止误删后来同步的同 ID 副本。其他 KeyVault 多存储修改仍采用同步前像补偿；无可信 journal 时才进入持久隔离并 fail-closed |
| P0 | 备份导入同时写 SwiftData 与 Keychain，后半段失败或崩溃可留下部分导入；空密文还可能错误绑定本机同 UUID 孤儿密文 | `backupImport` 复用同一持久 WAL 与所有权证明，运行期失败逆序补偿、崩溃后按持久 phase 回滚或前滚；无论备份密文是否为空都先检查本机同 UUID 条目，只有完全相同的密文允许恢复元数据，空值或冲突值均跳过，不能暴露既有孤儿 |
| P0 | 同路径 journal 的多个实例或多个 macOS 进程可能并发 `begin` 覆盖恢复标记；启动恢复也可能拿陈旧 record 处理新事务 | 同路径实例共享进程锁，Darwin 上再用 `flock` 做跨进程排他；启动先封住共享 `StorageMutationGate`，取得恢复排他 permit 后重新 `load` 并完整核对 transaction record，transaction id 不匹配时拒绝变更或清除 |
| P0 | 全量清除是多存储不可逆流程，中途锁定/崩溃可留下无法恢复的半删除状态 | `DurableDataEraseJournal` 使用文件、临时文件原子替换及文件/目录同步保存阶段；最终授权、写栅栏 seal 与首个 journal 标记同一同步提交，标记失败零删除并撤销新 seal；一旦标记成功，失败时保持 sealed，并由设备主人认证继续幂等删除，不依赖可能已被删除的应用密码 |
| P0 | 全量清除与普通写并发，旧事务可能在删除中补回数据，新事务可能在半删除状态落盘 | 进程级 `StorageMutationGate` 覆盖 Vault、使用方、偏好、主密码、备份口令、备份、权益等写事务；清除 seal 后等待此前已开始事务及其补偿结束，拒绝后来写；启动发现 pending journal 时预封口；清完仍属本 App 的剪贴板、清除 journal 后才重开 |
| P0 | macOS 本机非同步口令默认落入 legacy file-based Keychain，与 iOS/Catalyst 语义不一致 | 原生 macOS 所有主路径显式使用 Data Protection Keychain；只对历史本机口令做读取后迁移，legacy 查询显式指定 `false`，防止清理误删新域 |
| P0 | 应用密码失败计数仅在内存，强退重开可重置；工作因子与格式不便迁移 | Keychain 材料升级为版本化 payload；保存失败次数与延时；10 次锁定后只能走设备主人恢复；旧 v1 材料成功验证后原位升级 |
| P0 | CloudKit 同步偏好单例可出现重复行，旧实现按字典序挑一行，可随机降低安全 | 重复期对安全字段作保守合并：保护开关取开、时间取短、策略取强，并回写修复所有副本；用户之后显式验证降级仍可正常写全 |
| P0 | Mac 系统认证面板会导致 resign，用户在面板期间 Cmd-Tab 的真实离开可丢失 | 认证时暂存离开时刻，认证结束后根据宿主实际前台状态补做离开；普通系统框返回则不误锁 |
| P1 | 页面消失按粗粒度 owner 取消，可误取消后来页面已发起的同类请求 | 改为精确 `AuthenticationRequestHandle` 与 Task-local scope；普通页面只结束自己的请求，全局取消仅保留给真实后台/锁定 |
| P1 | `LAError` 被压成统一“失败/取消”，调试无法区分无设备密码、不可交互、上下文失效与系统中断 | 增加类型化错误和对应本地化，保留可诊断原因；用户取消不自动切换另一条认证路径 |
| P1 | 取用完再读偏好来推断“刚才是否真验证”，await 期间变更可伪造复用权 | 取用结果携带同一偏好快照下产生的验证证据；UI 不再二次推断 |
| P1 | 安全偏好在多个长寿命 SwiftData context 中可读到旧值 | 每次敏感读/条件写前回到持久化快照；回前台和 CloudKit 导入后重载 App 安全策略 |
| P1 | 剪贴板连续写、同文本外部写入、写后验证失败可导致误清或保留明文 | 用代次 + `changeCount` 原子 compare-and-clear；写后验证失败时在同一 MainActor 提交中条件回滚，旧计时器和所有权同步退役；Catalyst `.localOnly` 失败不降级到普通剪贴板 |
| P1 | 备份口令与细节页明文可在会话锁定后继续被使用/留在草稿 | 备份口令设置、删除、复制都走会话 lease 和真实 Keychain/剪贴板提交；密钥详情在锁定、真实离场、页面消失时清空原始与编辑明文 |
| P1 | 应用密码输入面若沿用普通文本输入，可带来智能标点、自动更正、不恰当提示或焦点残留 | 统一敏感密码输入契约并清理提交/取消后状态 |
| P1 | 「验证方式」子页从应用验证切到设备验证时，当前应用密码确认框挂在已被导航遮住的设置根页，必须返回才出现 | 确认框和持久化错误统一挂到整个 `NavigationStack`；增加请求代次与取消失效，迟到的认证结果不得提交；选中项以持久化源回读 |
| P1 | iPad 冷启动准备期立即回主屏可错过整轮生命周期通知；且 `UIApplication.didEnterBackground` 到达时 scene 快照可仍是 `.onScreenIdle`，导致立即锁定不记录离开 | 异步存储准备前就武装观察器；增加 `UIScene.didEnterBackground` 最终确认、全窗口汇总与单轮去重；只有全部离屏才起算自动锁，另一扇窗仍在操作时不全局撤权 |
| P1 | iPad 回主屏后立即点图标返回时，系统可在来得及发送 background 通知前已重新 active；而主屏离开与控制中心的首帧信号相同，首帧就锁会误锁，等 background 又会漏锁 | 立即档加入基于单调时钟绝对截止的有界候选观察，仅在全部离屏或原始窗口外观明确非 active 时确认；`didBecomeActive` 第一步取消并用 revision 拒绝迟到回调。候选期使用独立隐私遮挡与可逆 provisional authorization fence；真离开先升格正式撤权再解除临时栅栏，控制中心返回则保留原授权代次 |
| P1 | 启动期的 active / Cloud 安全偏好导入可与首次权威读取交叉，过早重开会话授权 | 以 `initialSecurityLoadCompleted + isPreferencesReady + userFacing` 统一收口授权悬挂；首次权威读取后再消费最新 Cloud 代次，启动前回调不得越过冷启动门闩 |

## 4. 与 Apple 系统认证的现行关系

- “设备验证”和组合档的系统路径都只创建一次 `.deviceOwnerAuthentication`。设备先用其实际支持的生物识别（Face ID / Touch ID / 其他 Apple 支持方式），然后在同一系统流程内转设备密码或 Mac 用户密码。
- 不再先调 `.deviceOwnerAuthenticationWithBiometrics` 然后创建第二个 `LAContext`；这是之前“又出现一次 Face ID”的直接原因。
- “使用应用密码”是 App 内用户显式点击的独立入口；系统取消或失败不会暗中自动提交应用密码。

## 5. 没有在 V1 偷偷引入的大改

真正达到高保障密码管理器架构，需要把可同步明文改为可同步密文，引入随机 DEK，每台设备使用 Secure Enclave / Data Protection Keychain 中受认证约束的包装密钥，并用应用密码派生的 KEK 提供另一条包装路径。这会同时引入新设备登记、恢复、轮换、遗忘密码和旧数据迁移协议。

因此它应是 V2 有数据迁移、恢复设计和回滚路径的独立项目，而不是在 v1.13.9 热修中直接改写用户已有 Keychain 数据。本轮采用的是“保留已验证主流、把授权与失效边界做成硬约束”，避免负向优化和数据破坏。

## 6. 历史工作包的用法

`v1.13.9-身份验证四档与主密码调整` 整个目录仍有审计价值，不删除；但只有 `19`、`20`、`21` 和本页是现行边界。旧的阶段提示词、实施分工和“最终计划”只是历史证据，不得重新执行，不得覆盖现行 spec 和已验证代码。

## 9. 当前边界

- 当前三平台自动回归表明本轮自动覆盖路径没有已知回归；这不等于宣称任何软件“绝对无 Bug”，也不替代 §8 明列的真实设备交互。
- 本次 iPad A/B 只证明该物理设备、当前系统与实测操作时序的端到端结果。真机 A 路径由 scene/application background 通知确认，没有直接命中仅 raw 外观的 probe-confirmed 分支；后者的证据是三平台自动测试，不冒充真机日志。
- Face ID / Touch ID / 设备密码 / Mac 登录密码由操作系统保护，真实交互必须由用户本人完成；自动测试不能伪造生物识别成功证据。
- V2 密文、DEK/包装密钥、新设备登记、恢复、轮换与迁移仍是独立项目，不在本次热修中偷渡。

## 10. 冻结决定

- 2026-09-24 用户明确要求：`v1.13.9` 只收口验证方式连续切换、完成 iPad 真机测试，然后冻结密码/身份验证功能。手机连续切换已通过，iPad 上 A/B 相反生命周期路径已通过，三平台全量回归已通过，该范围达到冻结条件。
- 从本记录起，`v1.13.9` 不再追加身份验证功能、不再为“顺便优化”改动认证与生命周期主链；只有新的可复现 P0/P1 回归才可按变更机制解冻。
- “密码与身份验证代码冻结”不等于“版本已发布”：双设备 CloudKit/密码材料缺失、历史全矩阵人工验收、Archive、提交、上传和打 tag 仍是独立闸门，不得用本冻结结论代替。同步机制与 UI 重设计也应在后续版本独立实施，不再混入本热修。
