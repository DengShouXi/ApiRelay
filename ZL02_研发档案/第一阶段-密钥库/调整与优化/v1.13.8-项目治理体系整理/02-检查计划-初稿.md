# v1.13.8 项目治理体系整理：检查计划初稿

> 状态：等待 Grok 阶段 2 补充；不是最终检查计划。

## 一、安全与范围检查

- 开始前核对分支、HEAD、远程跟踪关系和工作区；确认原有内容只有未跟踪的 `tools/`。
- 整理后检查差异中是否出现 Swift、测试、Xcode 工程或其他业务代码。
- 对比 `main`、`origin/main`、`release/1.0.0`及其他受保护分支、标签的前后指向。
- 检查是否出现 rebase、amend、force push、删除分支、删除标签或其他历史重写。
- 确认 `tools/` 未被读取后改写、移动、清理、暂存或提交。
- 阶段2不得通过`fetch`或`pull`更新远程跟踪指针；只能记录本地可验证状态和无法验证的远程事实。
- 因工作包尚未被Git跟踪，阶段2应比较开始前后已有工作包文件，确认只新增指定的`03`报告。

## 二、v1.13.8 身份验证路牌检查

搜索所有包含 `v1.13.8`、`1.13.8`、身份验证、四档、identity auth 等含义的现行文件。每个结果必须归入：

1. 历史事实，可以保留；
2. 当前治理整理，应继续属于 `v1.13.8`；
3. 未来身份验证，应改为计划中的 `v1.13.9`；
4. 含义不清，必须阻塞并交由用户判断。

验收标准：不能再有任何现行实施路牌要求在 `v1.13.8` 开发身份验证；也不能把尚未创建的 `v1.13.9`写成已经存在或已经完成。

## 三、唯一权威与冲突裁决检查

- 只有 ZL00 能定义“哪个文件负责哪类决定”和冲突怎样裁决。
- 根 AI 入口、Cursor 规则、ZL01、ZL02、Spec Kit 和流程文件只能引用该机制，不能复制出另一套最高规则。
- 任取以下冲突进行情景测试：Spec Kit 与 ZL02 冲突、计划与上传流程冲突、当前状态与历史记录冲突、AI 对话与正式规格冲突。
- 每种冲突必须得出唯一处理路径：停止受影响动作、收集证据、用户决定、回写权威文件、更新中文状态、一致性检查、恢复执行。
- 检查是否存在循环引用、互相授权或“最新版自动获胜”。
- 检查 ZL00 是否只保存治理方法论，没有混入本次具体工作的计划、检查、实施或审计报告。

## 四、工作来源分流检查

- 通过 Spec Kit 框架发起的建设全过程是否保存在 `ApiRelay/specs/`；
- 实际使用后产生的非 Spec Kit 调整全过程是否保存在 ZL02；
- ZL01 是否保留中文状态、说明、AI对话索引和演进记录，同时没有变成第三套完整技术过程档案；
- 本工作包是否留在 ZL02 的“第一阶段-密钥库/调整与优化”固定路径；
- ZL02 中获批且需要改变正式规格的结论是否回写 `ApiRelay/specs/`，同时保留 ZL02 原始过程证据；
- 是否避免把同一份完整计划同时复制到 ZL00、Spec Kit 和 ZL02，形成重复权威。

## 五、Spec Kit 与 ZL02 双向反馈检查

验证闭环是否完整：

`Spec Kit 当前基线 → 实施/使用 → ZL02 事实证据 → 研究或候选调整 → 用户批准 → 回写 Spec Kit → ZL01 更新中文状态 → 再实施和验收`

重点检查：

- ZL02 可以挑战甚至推动改变主体结构；
- 未批准建议不能暗中覆盖 Spec Kit；
- 已批准变更不能长期只留在 ZL02；
- “已经接受但尚未回写”的状态会阻止受影响的正式实施和上传。

## 六、ZL01 可读性检查

由非技术人员视角从 `00-从这里开始.md`进入，确认能用简明中文找到：

- 当前版本和分支；
- 当前正在做什么；
- 下一步是什么；
- 当前冲突或阻塞；
- 最近批准了什么；
- 正式规格在哪里；
- 事故和优化证据在哪里；
- 规则冲突时听谁、怎么办。

稳定说明不得大量夹带会迅速过期的当前状态和动态数字；英文或代码名必须有中文解释。

## 七、ZL02 分类检查

- 顶层按真实产品阶段组织，而不是把所有事故混在一起；
- 每个阶段有阶段总览；
- 每次事故有独立文件夹；
- 事故内部保留总览、复盘、执行须知、实施步骤和验收材料；
- 不创建没有真实材料的事故，不伪造已完成阶段；
- 现有第一次事故的事实内容没有在移动时丢失或改写。
- 每个非 Spec Kit 调整和优化也有独立文件夹，能够保存其计划、检查、实施、审计和结果。

## 八、链接、路径与锚点检查

- 检查所有受影响 Markdown 相对链接的目标是否存在；
- 检查 ZL02 旧路径引用是否清零；
- 检查目录索引是否覆盖新增文件；
- 检查显式锚点、UUID 或跳转标识是否重复、缺失或失效；
- 不引入本机绝对路径或 `file://` 链接；
- 文件移动前后分别记录引用清单。

## 九、防止状态再次漂移

- 当前版本、当前分支、正在做什么和下一步只能有一个主要维护位置；
- 稳定规则文件通过链接读取动态状态，不重复抄写；
- 文件数、代码行数和测试数等易变化数字不应成为长期手工维护的权威；
- 变更必须有“提议、已批准、已回写、已验收”等明确状态；
- 上传闸门必须能够发现“已批准但尚未回写”的决定；
- AI 新对话开始时能从统一入口找到当前权威和状态。

## 十、上传流程可执行性检查

- 现行上传流程、Cursor始终生效规则、`BRANCHES.md`、ZL01的AI记录和上传记录是否要求同一次上传中互相更新；
- 这些要求是否与“最终验收后不再修改治理内容”“只提交一次”发生冲突；
- 上传前无法知道的日期、提交hash或远程结果是否被要求提前填写；
- 最终计划是否明确给出真实可执行的先后顺序，而不是把冲突留到阶段8；
- 阶段8是否有精确暂存清单、暂存差异复核、`tools/`排除和禁止force push保护；
- 阶段9是否能够不依赖Grok口头报告，直接核对本地与远程。
