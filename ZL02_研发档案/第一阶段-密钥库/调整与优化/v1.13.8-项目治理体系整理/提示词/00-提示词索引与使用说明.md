# 提示词索引与使用说明（ZL02非Spec Kit调整）

> 固定工作包：`ZL02_研发档案/第一阶段-密钥库/调整与优化/v1.13.8-项目治理体系整理/`

> 分类：实际使用后产生的非 Spec Kit 治理调整。ZL00只保存方法论，`ApiRelay/specs/`保存Spec Kit工作全过程，本工作包完整保留在ZL02。

## 使用方法

1. Cursor必须打开仓库根目录；该目录应同时包含`.git/`、`ApiRelay/`、`ZL01_具体说明/`和`ZL02_研发档案/`。不要只打开内部`ApiRelay/`目录。
2. 每次只复制当前阶段文件中代码框里的完整提示词。
3. 不需要复制以前的聊天、计划或检查报告；模型会从固定工作包读取。
4. 每个阶段结束后先查看其结论，再启动下一阶段。
5. 本页不手写“当前进行到哪一步”。不确定时使用 `通用-只检查当前阶段.md`，让模型根据实际阶段产物和 Git 状态判断。

## 两项禁止自动跨越的关口

- 阶段 4：必须由用户明确批准最终计划；仅仅生成最终计划不等于批准。
- 阶段 8：必须由用户明确授权提交和上传；验收通过不等于授权上传。
- 阶段 8 固定采用“内容提交 A + 四文件记账提交 B”，然后把 `v1` 快进到 B；不得现场改为一次或递归增加第三次提交。
- 若 `09` 已写明验收不通过，不得覆盖或重跑原阶段 7；必须依次执行 7A → 7B → 7C。只有最新的 `12-Codex第二轮复验报告.md` 明确通过，才可等待阶段 8 授权。

## 提示词维护规则

- 固定路径和阶段产物名称原则上不变。
- 阶段 3 若调整最终计划，Codex必须同步复核阶段 4 至阶段 9 的提示词，并在回复中说明是否改动。
- 后续任何模型发现提示词与实际状态冲突时，必须停止，在当前阶段报告中指出冲突；不得绕开提示词自行执行。
- 提示词不能降低用户批准权、业务代码保护、`tools/`保护、历史保护和禁止 force push 等安全要求。
- 阶段3不仅要定稿计划，还必须根据检查结果逐份复核后续提示词；不得把尚待查清的上传冲突拖到阶段8临时处理。
- 每份阶段报告和最终计划必须带有阶段、时间、分支、起始HEAD和输入文件标识；标识不匹配的旧文件不能作为下一阶段依据。
