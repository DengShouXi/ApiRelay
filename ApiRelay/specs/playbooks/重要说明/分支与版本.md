## 现行命名（记这套即可）

| 种类 | 写法 | 例子 |
|------|------|------|
| 规划小迭代 | `plan.N` | `plan.1` |
| 规划 tip | `plan` | `plan` |
| 产品大阶段 tip | `v1` / `v2` / `v3` | `v1` |
| 产品小迭代 | `v{阶段}.{小迭代}` | `v1.13` |
| 上架后热修（Git 分支） | `v{阶段}.{小迭代}.{热修}` | `v1.13.1` |
| 上架 tag（仅商店，不是分支） | `release/N.0.0` | `release/1.0.0` |
| 稳定可发布 | `main` | 与当时上架 tag 同 tip，直到下次送审 |

旧名 `v0.0.*` / `v0.1.*` 等已废弃，远程应已清理；勿再建。

## 三个容易混的概念

Git 里真正存代码的是**某一次提交**。分支和 tag 都只是给这次提交起名字：

| | 分支 | Tag |
|---|---|---|
| 像什么 | 还能往下翻的书签 | 贴在某一页上、一般不再换页的名牌 |
| 会不会跟着新 commit 走 | 会（关账的小迭代则冻住，改开热修分支） | 不会 |
| 用来回答 | 「现在做到哪」 | 「当时上架的是哪一包」 |

因此现在可以同时有：分支 `v1.13`、分支 `main`、**tag** `release/1.0.0`，三者内容可以完全相同。  
**不要**再开一条同名分支叫 `release/1.0.0`——tag 已经是那块名牌，分支和 tag 同名会搞混 checkout / push。

两套数字也不要混：

| 数字 | 谁在用 |
|------|--------|
| `v1.13` / `v1.13.1` | Git 开发 / 热修分支 |
| `1.0.0` / `1.0.1` | App Store 给用户看的版本（`MARKETING_VERSION`） |

下次再送审才把商店号改成 `1.0.1`，并另打 **tag** `release/1.0.1`。那不是现在这条热修 Git 分支的名字。

## 上架后修 bug 怎么走

```text
已冻结：  v1.13  +  tag release/1.0.0  +  main（商店 1.0.0）
这次修：  新分支 v1.13.1   ← 保存并上传到这里
tip：     v1 前进到 v1.13.1
不要动：  v1.13、tag、默认也不动 main
```

禁止：把修改推回 `v1.13`；开 `release/1.0.1` 分支；把 `v1.13` 改名为 `release/1.0.0`。
