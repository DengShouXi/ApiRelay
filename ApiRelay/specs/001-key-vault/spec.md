# Product Specification: ApiRelay（全阶段产品规范）

**Feature Branch**: `v1` / `v1.N`（V1；文档目录仍为 `specs/001-key-vault/`）

**Created**: 2026-08-04

**Status**: Approved — 分三阶段实施，阶段范围见 [ROADMAP.md](../ROADMAP.md)

**Input**: User description: "存入各平台 API 密钥，为每个使用密钥的工具分配独立密钥，按上游平台与使用方两个维度查看用量；不含 App 内聊天调用窗口；自建中转作为独立阶段实施。"

## 阶段范围速查

> **本文档覆盖全部三个阶段的需求**，因为数据模型必须一次性按三阶段设计才能避免破坏性迁移
> （见 [data-model.md](./data-model.md) §10）。**每条需求都标注了所属阶段**；
> 阶段范围的唯一权威是 [ROADMAP.md](../ROADMAP.md)。

| 阶段 | 分支 | 范围一句话 | 用户故事 |
|------|------|-----------|----------|
| **V1** | `v1` | 密钥保险库：保管、分发、指派、双视角。**完全不联网调上游**。上架 **1.0.0** | US1、US2、US5、US6 |
| **V2** | `v2` | 用量看板、关系图、App 内签发密钥、**密钥可用性检测**。上架 **2.0.0** | US3、US4、US8、US9、US10 |
| **V3** | `v3` | 中转服务：下游配置永久不用改 + 完全自主的逐笔统计。上架 **3.0.0** | US7 |

**当前实施阶段：V1。** V2/V3 的需求在本文中只作为设计约束存在，
**V1 的界面 MUST NOT 出现它们的入口**。

## 术语表（务必区分两类「平台」）

本产品涉及两类完全不同的平台，全部文档、代码命名与界面文案 MUST 严格区分，MUST NOT 混用「平台」一词指代二者：

| 术语 | 含义 | 举例 | 代码中的名称 |
|------|------|------|--------------|
| **上游平台**（API 提供方） | 签发 API 密钥、提供模型服务、产生消费的一方 | OpenAI、Claude、Google、OpenRouter、DeepSeek、阿里百炼、火山引擎、硅基流动 | `UpstreamAccount.platform` |
| **使用方工具**（消费端） | 消费密钥、发起调用的客户端软件 | VS Code、Cursor、OpenCode、Trae | `ConsumerTool` |

**密钥是二者的连接物**：一把密钥由某个**上游平台**签发，被指派给一个或多个**使用方工具**使用。

**两类都支持自定义添加**（FR-007a）：产品内置常见项作为预置清单，用户 MUST 能自行添加任何未预置的上游平台（含自定义接入地址）与使用方工具。预置清单随应用更新扩充，MUST NOT 覆盖或删除用户自建项。

## 产品概述

面向苹果生态下的 AI 开发者与重度 AI 工具使用者。解决三个真实痛点：

1. **密钥分散**：DeepSeek、OpenAI、Claude、OpenRouter 各有账号后台，密钥散落在浏览器书签、备忘录、聊天记录里。
2. **一把密钥到处粘贴**：同一把密钥填进 VS Code、OpenCode、扣子等多个工具，一旦泄露无法判断从哪漏的，只能全部作废重配。
3. **用量不透明**：每个平台的用量要分别登录各自后台查看，没有跨平台的统一视图，更看不出「哪个工具在烧钱」。

阶段一交付一条可独立闭环的主流程：**登记上游平台账号 → 为每个使用方工具分配一把独立密钥 → 经身份确认后复制到系统剪贴板**。
（**按「上游账号」与「使用方工具」查看用量与余额属 V2**，见阶段范围速查；V1 完全不联网调上游。）

**交付边界**：产品的职责终点是**系统剪贴板**。产品 MUST NOT 与任何外部工具（VS Code、Cursor、扣子等）建立集成、写入其配置文件或代其填充；粘贴动作由用户自行完成。「使用方工具」在产品内仅是一个归属标签。

**平台范围**：本期同时覆盖 iPhone 与 Mac。

**本阶段明确不含**：App 内的聊天或调用窗口（产品不做 AI 对话客户端）；自建中转服务（推迟到阶段三，见 User Story 7 与 Out of Scope）。

**核心机制说明（业务层面）**：阶段一的「一工具一密钥」依靠**上游平台原生支持多密钥**实现——用户在平台侧（或在本产品内，见 US3）创建多把密钥，本产品负责保管、标注归属、安全分发与用量归集。本产品**不介入实际 API 流量**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 安全保管密钥并交付给目标工具 (Priority: P1)

作为 AI 开发者，我希望把各平台的 API 密钥集中存进一个受生物识别保护的保险库，并在需要时安全地取出交给目标工具，以便不再把密钥散落在备忘录和聊天记录里。

**Why this priority**: 保管与交付是后续一切能力的前提。没有它，分配、统计、付费边界都无从谈起。这也是唯一一条即使单独存在也已具备完整产品价值的故事。

**Independent Test**: 仅启用本故事即可完整验证：新增一条密钥、经身份确认后查看明文、经身份确认后复制到剪贴板、确认剪贴板在设定时间后被清除、删除密钥；免费用户达到上限时无法继续新增。

**Acceptance Scenarios**:

1. **Given** 用户尚未保存任何密钥，**When** 用户新增一条密钥并填写名称、所属上游平台与密钥内容，**Then** 该密钥出现在列表中，明文默认以掩码显示。
2. **Given** 验证方式为默认档（生物识别或设备密码），**When** 用户发起「查看明文」或「复制」，**Then** 系统先要求身份确认（生物识别失败自动回退设备密码）；通过后取出明文；失败或取消则不取出。
3. **Given** 用户已将验证方式设为「不验证」，**When** 用户发起「查看明文」或「复制」，**Then** 系统直接取出明文，不弹出任何验证；该设置对查看与复制**同时生效**，不存在只关闭其中之一的可能。
3a. **Given** 用户发起「复制」并已通过门闩，**When** 明文写入剪贴板，**Then** 系统在设定时长（默认 2 分钟）后自动清除该内容；若用户开启「禁用通用剪贴板」，该内容 MUST NOT 被同步到用户的其他设备。
4. **Given** 用户已复制密钥且尚未到清除时间，**When** 用户手动清除或再次复制其他内容，**Then** 系统不再对原内容执行延时清除，且不误清用户后续复制的无关内容。
5. **Given** 列表中已有密钥，**When** 用户确认删除，**Then** 该密钥从主列表移除并进入「最近删除」回收站；**30 天内**可恢复；回收站期间 Keychain 明文仍保留但主列表不可见、不可复制（FR-006）。
5a. **Given** 密钥在回收站且未满 30 天，**When** 用户经不可关闭的身份确认后选择恢复，**Then** 密钥回到主列表且明文可按既有门闩规则取出，指派关系保持。
5b. **Given** 密钥在回收站已满 30 天，或用户在回收站选择「立即删除」，**When** 永久清除执行，**Then** 本机 Keychain 对应条目被删除且不可再恢复；历史用量记录保留并标注「已删除」。
6. **Given** 免费用户已保存 3 把密钥，**When** 尝试新增第 4 把，**Then** 系统拒绝并说明已达免费上限及升级后可解锁无限密钥。
7. **Given** 免费用户已达上限，**When** 用户删除一把（移入回收站）后再次新增，**Then** 允许新增——回收站中的密钥**不计入**免费额度。

### User Story 2 - 一工具一密钥的分配与双视角查看 (Priority: P1)

作为同时使用多个 AI 工具的开发者，我希望为每个工具分配一把专属密钥并记录归属关系，然后既能「按上游平台」也能「按使用方工具」两个角度查看，以便一眼看清谁在用哪把钥匙，泄露时能精准定位并只作废那一把。

**Why this priority**: 这是产品区别于普通密码管理器的核心价值，也是用户最初的动机（隔离与可定位）。与 US1 共同构成最小可用闭环。

**Independent Test**: 在已有若干密钥的前提下，为每把密钥指定使用方，然后分别切换到两种分组视角，验证同一批数据在两个角度下都能正确归集与展开，无需依赖用量统计或付费能力。

**Acceptance Scenarios**:

1. **Given** 用户已保存一把密钥，**When** 用户为其指定使用方工具（如「VS Code」），**Then** 该归属关系被保存并在两种视角下均可见。
2. **Given** 用户在同一上游平台下保存了多把密钥并分别指定了不同使用方，**When** 用户切换到「按上游平台」视角，**Then** 可看到该平台节点，展开后列出其下所有密钥及各自的使用方。
3. **Given** 同上，**When** 用户切换到「按使用方」视角并展开某个工具，**Then** 可看到该工具持有的所有密钥及各自所属的上游平台（可跨平台）。
4. **Given** 某把密钥尚未指定使用方，**When** 用户查看「按使用方」视角，**Then** 该密钥归入「未分配」分组，不被隐藏或丢失。
5. **Given** 用户怀疑某个工具泄露了密钥，**When** 用户在该工具下定位到对应密钥并作废，**Then** 其他工具持有的密钥不受影响，用户可清楚知道仅需在该工具处更换。
6. **Given** 用户需要新增使用方名称，**When** 用户输入一个预置列表中不存在的工具名，**Then** 系统允许自定义并在后续可复用该名称。

### User Story 3 - 在 App 内直接签发与作废密钥 (Priority: P1)

作为使用 OpenRouter 等支持密钥管理接口的平台的用户，我希望不必打开浏览器登录后台，直接在本产品内创建一把新密钥、给它命名、设置消费上限，并在怀疑泄露时一键禁用，以便把「一工具一密钥」这套习惯的操作成本降到最低。

**Why this priority**: 这是本产品相对「手工记录型」工具的决定性差异点，也是让用户直观感到价值的功能。它依赖平台能力，仅部分平台可用，故与 US1/US2 并列 P1 但范围受限。

**Independent Test**: 在已配置具备密钥管理权限的凭证前提下，于 App 内创建一把新密钥并确认其在平台侧真实存在，随后禁用它并确认平台侧状态同步，无需依赖用量统计。

**Acceptance Scenarios**:

1. **Given** 用户已为某支持平台配置了具备密钥管理权限的凭证，**When** 用户在 App 内发起「新建密钥」并填写名称与可选消费上限，**Then** 系统在平台侧创建该密钥，将返回的明文存入保险库，并自动登记其上游平台归属。
2. **Given** 平台仅在创建时返回一次明文，**When** 创建成功但本地保存失败，**Then** 系统必须明确告知用户「密钥已在平台侧创建但本地未保存，请立即前往平台后台处理」，不得静默丢失。
3. **Given** 用户已在 App 内创建的密钥，**When** 用户发起「禁用」或「删除」，**Then** 系统在平台侧执行相应操作，并在本地同步状态。
4. **Given** 用户使用的平台不支持密钥管理接口（如 DeepSeek），**When** 用户查看该平台，**Then** 系统明确说明该平台需前往官网创建密钥，并提供跳转入口，不得让「新建」按钮看起来可用却失败。
5. **Given** 用于密钥管理的凭证是高权限凭证，**When** 用户配置它，**Then** 系统必须在配置界面明确告知其权限范围与风险（可创建密钥、可产生消费），并与普通密钥同等或更严格地保护。
6. **Given** 用户未配置管理权限凭证，**When** 用户使用产品其他功能，**Then** 全部不受影响（管理能力为可选增强，非必需前置）。

### User Story 4 - 按两个维度查看用量与余额 (Priority: P2)

作为需要控制成本的开发者，我希望看到每把密钥、每个上游平台、每个使用方工具各消耗了多少，以及账户还剩多少余额，以便判断钱花在哪、哪个工具异常。

**Why this priority**: 直接回应「用量不透明」痛点，是主要的付费吸引力之一。但主流程（保管与分发）不依赖它，故排在 P1 之后。

**Independent Test**: 在已配置相应凭证并产生过真实用量的前提下，刷新用量并验证三级归集（单密钥 / 按上游平台 / 按使用方）数值自洽，以及在平台能力不足时给出正确的说明而非空白。

**Acceptance Scenarios**:

1. **Given** 用户已为支持按密钥统计的平台配置了相应凭证，**When** 用户刷新用量，**Then** 可见每把密钥的用量数值，且「按上游平台」与「按使用方」两个维度的汇总等于其下各密钥之和。
2. **Given** 平台仅提供 token 数而不提供按密钥的费用，**When** 系统展示费用，**Then** 依据可追溯的单价规则估算，并标明「按 {模型} {生效日} 单价估算」，不得呈现为平台官方账单数字。
3. **Given** 平台不支持按密钥拆分用量（如 DeepSeek 仅提供账户余额），**When** 用户查看该平台下的密钥，**Then** 系统在该平台节点显示账户级余额，并在密钥级明确标注「该平台不支持按密钥统计」，不得留空让用户误以为是故障或用量为零。
4. **Given** 用户从未配置统计所需凭证，**When** 用户打开用量界面，**Then** 系统说明需要配置何种凭证才能看到数据，以及不配置时仍可使用的功能范围。
5. **Given** 设备无网络或平台接口返回失败，**When** 用户查看用量，**Then** 系统展示上一次成功获取的数据并标注其获取时间，同时提示本次刷新失败的可读原因；本地已有数据不丢失。
6. **Given** 平台接口发生变更导致解析失败，**When** 用户刷新，**Then** 该平台的统计降级为「暂不可用」并给出提示，其他平台的统计与产品其他功能不受影响。
7. **Given** 单价规则被修改，**When** 用户查看历史用量，**Then** 已展示过的历史估算值不被静默改写，或提供可追溯的口径变更说明。

### User Story 10 - 检测密钥是否还能用 (Priority: P2 — 阶段 V2)

作为把十几把密钥收进保险库的用户，我希望能手动点一下就知道哪些密钥已经不能用了（在平台后台被我自己删过、被平台禁用、或者当初录入时就存错了），失效的密钥在列表上直接带个醒目的标记，以便我不用逐个去各平台后台核对。

**Why this priority**: 保险库存久了必然出现「这把还有效吗」的疑问，而逐个登录平台后台核对的成本极高。它不产生新数据，只是给已有密钥补一个状态，因此不影响任何既有需求。

**归属阶段的理由（DC-017）**：检测必然要联网调上游，而 V1 的定义性边界是**完全不联网调上游**。探活归 V2；V1 以 **1.0.0** 单独上架后，用户需升级到 **2.0.0** 才获得该能力。同时保住了 V1「零网络」带来的全部简化。V1 只需在数据模型中预留字段（FR-055）。

**与 US4 的区别**：检测**只需要密钥自己**，不需要管理类高权限凭证。因此像 DeepSeek 这种「不支持按密钥统计用量」的平台，检测照样可用——这是本故事独立于用量统计的价值来源。

**Independent Test**: 在保险库中放入一把有效密钥与一把已在平台后台删除的密钥，手动触发检测，验证前者标为有效、后者标为已失效；断网后再检测，验证两者都标为「未能确认」且**保留上一次的结论与时间**，而不是被判为失效。

**Acceptance Scenarios**:

1. **Given** 保险库中有一把有效密钥，**When** 用户点该密钥的「检测」，**Then** 系统向其上游平台发起一次最小请求，结果标注为「密钥有效」并记录检测时间。
2. **Given** 某把密钥已在平台后台被删除或禁用，**When** 用户检测它，**Then** 该密钥被标注为「已失效」，且在两种分组视角的列表中都带醒目标记（感叹号）。
3. **Given** 保险库中有从未被检测过的密钥，**When** 用户查看列表，**Then** 这些密钥 **MUST NOT 带任何失效标记**——未检测不等于失效。
4. **Given** 设备无网络，或平台返回 429（限流）、超时、5xx，**When** 用户检测，**Then** 结果为「未能确认」并给出可读原因；**MUST NOT 判为失效**，且**上一次的结论与时间戳 MUST 保留**。
5. **Given** 某把密钥有效但账户余额已耗尽，**When** 用户检测，**Then** 结果表述为「密钥有效」，**MUST NOT 表述为「可用」**——余额与模型权限并未被检查。
6. **Given** 用户在列表页发起「全部检测」，**When** 检测执行，**Then** 请求串行且受节流，同一把密钥在冷却期内 MUST NOT 被重复检测。
7. **Given** 用户从未主动检测，**When** 应用启动或进入前台，**Then** 系统 **MUST NOT 自动执行检测**——这是用户未预期的网络流量，也会撞上平台限流。
8. **Given** 用户为某自定义平台录入了密钥而系统不知道该平台的检测端点，**When** 用户检测，**Then** 系统说明「该平台未接入检测」，**MUST NOT 显示失效标记**。
9. **Given** 用户已把取出明文的验证方式设为需要生物识别，**When** 用户发起「全部检测」，**Then** 全程 **MUST NOT 弹出任何身份验证**——明文没有被交给用户（宪法 VIII）。

### User Story 5 - 付费解锁无限密钥 (Priority: P2)

作为把「一工具一密钥」推广到全部工具的用户，我希望一次性买断解锁无限密钥数量，以便不再受免费额度限制。

**Why this priority**: 构成变现边界，须在本阶段可验证权限开关，但排在核心主流程之后。

**Independent Test**: 在免费态与已购态之间切换同一设备，验证密钥数量上限的锁定与解锁表现，以及恢复购买流程。

**Acceptance Scenarios**:

1. **Given** 免费用户已达密钥数量上限，**When** 用户完成购买，**Then** 数量限制立即解除，可继续新增。
2. **Given** 用户曾在其他设备购买过，**When** 用户使用「恢复购买」，**Then** 权益在本设备恢复生效。
3. **Given** 用户已购买并保存了超过免费上限数量的密钥，**When** 因退款等原因权益失效，**Then** 超出部分**只读保留**（可查看元信息、可复制、可删除），仅禁止新增，不得强制删除或隐藏用户数据。
4. **Given** 用户处于免费态，**When** 用户使用保管、分配、双视角查看、用量统计等能力，**Then** 均可正常使用（免费态的唯一限制是密钥数量）。

### User Story 6 - 安全与偏好设置 (Priority: P2)

作为注重安全的用户，我希望自行决定进入 App 是否需要生物识别、复制前是否二次确认、剪贴板多久清除、界面深浅色等，并能加密备份与恢复我的保险库。

**Why this priority**: 设置项支撑 US1 的安全承诺（如复制前确认、剪贴板清除是 US1 验收项的开关），且备份恢复直接关系用户数据资产安全。但它依附于主功能存在。

**Independent Test**: 逐项切换开关并验证对应行为立即生效；执行一次加密导出后在另一环境导入，验证保险库可恢复且导出文件在无口令时不可读。

**Acceptance Scenarios**:

1. **Given** 用户开启「打开 App 需要生物识别」，**When** 用户重新进入 App，**Then** 必须通过身份确认才能看到内容。
2. **Given** 用户开启「在应用切换器中隐藏」，**When** 用户切到多任务界面，**Then** 本产品的预览画面被遮挡。
3. **Given** 用户执行加密导出，**When** 在另一环境用正确口令导入，**Then** 保险库内容可恢复；**When** 口令错误或缺失，**Then** 导出文件中的敏感内容不可被读取为明文。
4. **Given** 用户开启余额不足或密钥失效提醒，**When** 条件满足且系统允许后台刷新，**Then** 用户收到通知；系统 MUST NOT 向用户承诺实时性（文案须体现「在下次刷新时检查」）。
5. **Given** 用户切换外观为浅色/深色/跟随系统，**When** 设置生效，**Then** 界面立即响应且重启后保持。
6. **Given** 用户执行「清除全部数据」并完成不可关闭的身份确认与二次确认，**When** 操作完成，**Then** 本产品写入的 Keychain 条目、SwiftData/CloudKit 用户数据与本机刷新状态全部清除；**StoreKit 已购权益不受影响**（可经「恢复购买」重新生效）；同步开启时其他已登录同一 iCloud 账号的设备上的对应同步数据亦被清除（FR-061）。

### User Story 8 - 关系图：一眼看清密钥的分布结构 (Priority: P2 — 阶段 V2)

作为管理着十几把密钥、七八个工具的用户，我希望有一张图直观呈现「平台 — 密钥 — 使用方」的连接关系，以便一眼看出哪个工具用了哪些平台的密钥、哪把密钥在闲置、哪个平台被哪些工具依赖。

**Why this priority**: 密钥数量少时列表足够；数量上来后列表只能看到局部，看不到整体结构。这张图不产生新数据，是对已有数据的可视化，因此不影响任何既有需求，可独立开发与交付。

**形态裁决（DC-008）**：做成**三列桑基式关系图**（左：平台账号 / 中：密钥 / 右：使用方工具，用曲线连接），**不做自由布局的思维导图**。理由是本产品的数据是三层分明的，且「一把密钥属于多个平台」在技术上不存在——真正的网状部分只有「平台 ↔ 使用方」这一层多对多关系，它经密钥间接连接。三列布局比自由布局更易读，且不需要自研力导向布局算法（宪法第 III 条下无第三方库可用）。

**Independent Test**: 在已有若干密钥与使用方的前提下打开关系图，验证三列节点与连线正确反映指派关系，点击节点能高亮其全部关联路径；不依赖用量数据即可通过基本验证（有用量时连线粗细映射金额）。

**Acceptance Scenarios**:

1. **Given** 已有多平台多密钥且部分已指派，**When** 用户打开关系图，**Then** 三列节点与连线正确反映当前指派关系，未指派的密钥连向明确的「未分配」节点。
2. **Given** 关系图已打开，**When** 用户点击某个使用方节点，**Then** 系统高亮该工具持有的全部密钥及其所属平台，其余路径淡化。
3. **Given** 已有用量数据，**When** 用户查看关系图，**Then** 连线粗细映射用量金额，且无法统计用量的平台其连线 MUST 以明确的样式区分并说明原因，MUST NOT 呈现为「用量为零」。
4. **Given** 在 iPhone 上打开，**When** 密钥数量较多，**Then** 系统 MUST 提供可读的降级形态（紧凑版或明确的「请在 Mac 上查看」提示），MUST NOT 呈现为无法辨认的重叠图形。

### User Story 9 - 加密传递：把密钥安全地交给同事或朋友 (Priority: P3 — 阶段 V2)

作为需要把某把密钥交给同事或朋友的用户，我希望生成一个受口令保护的加密文件而不是直接把明文贴进聊天窗口，以便至少不在聊天记录里留下永久可读的明文。

**Why this priority**: 用户的现状是直接发微信/邮件明文。本能力用极低的成本（复用 FR-022 的加密备份）把这个行为变得安全得多。放在 V2 而非 V1，是为了让 V1 保持「个人保险库」这一单一心智。

#### 「传递」与「共享」是两件事，措辞 MUST NOT 混用（DC-016）

| | **加密传递**（V2，本故事） | **共享**（V3，见 US7） |
|---|---|---|
| 对方拿到 | **你的原始密钥明文** | 一把只对他有效的中转密钥 |
| 能否撤回 | **不能**。只能去平台后台作废，而那会同时打断你自己在用的工具 | **能**，单独撤销这一把，你自己不受影响 |
| 他用了多少 | **算不出**。平台只按密钥统计，你和他的消费混在一条记录里 | 单独统计 |
| 能否限额 | 不能 | 能 |
| 他泄露了 | 责任在你，且泄露的是**原始密钥** | 撤销那一把即可，原始密钥他从未见过 |

因此 V2 的能力 MUST 命名为「加密传递」而 MUST NOT 命名为「共享」「协作」等暗示可管控的措辞。真正的共享属 V3。

**Independent Test**: 勾选若干密钥生成加密文件，在另一台设备（另一个 Apple ID）的应用中用口令导入，验证密钥可用；验证无口令时无法读出明文；验证流程中出现不可忽略的风险告知。

**Acceptance Scenarios**:

1. **Given** 保险库中有若干密钥，**When** 用户勾选其中若干并发起加密传递，**Then** 系统经不可关闭的门闩确认后生成受口令保护的加密文件，并经**系统分享面板**交付；该文件 MUST NOT 经过本产品或开发者的任何服务器。
2. **Given** 加密文件已生成，**When** 在流程中，**Then** 系统 MUST 展示不可忽略的告知：**传出后无法撤回**、**对方产生的消费记在你的账上**、**多数上游平台的服务条款禁止将密钥分享给第三方**。
3. **Given** 接收方获得文件与口令，**When** 他在自己的应用中导入，**Then** 密钥进入其保险库并标注来源为「他人传递」；口令错误时 MUST NOT 泄露任何明文。
4. **Given** 用户误以为可以撤回，**When** 查找撤回入口，**Then** 系统 MUST NOT 提供任何形式的「撤回」或「失效」按钮，且 MUST 说明正确做法是前往平台作废该密钥并了解其影响范围。

### User Story 7 - 中转服务：让下游配置永久不用改 (Priority: P3 — 阶段 V3)

作为把同一批密钥配到七八个工具里的用户，我希望在自己的云账号上架一层中转：工具里配置的是**中转密钥**，指向我自己的中转服务；当上游平台的原始密钥失效或我想更换时，**我只在中转服务里换掉原始密钥，所有工具的配置一行都不用动**。

**Why this priority**: 依赖服务端与新技术栈，且会使用户的请求内容流经中转（重大隐私变更），风险最高，故排在最后。但**其产品价值是三个阶段里最高的**——见下方精髓说明。

#### 中转的精髓：稳定的间接层（此前理解有误，已更正）

早期文档把中转理解为「一把密钥拆成多把、实现隔离」。**这只是次要好处。** 真正的精髓是：

```text
【无中转】VS Code ──直连──▶ DeepSeek
          DeepSeek 密钥失效 ⇒ 逐个打开 VS Code、OpenCode… 改配置

【有中转】VS Code ──中转密钥──▶ 中转服务 ──原始密钥──▶ DeepSeek
          DeepSeek 密钥失效 ⇒ 只在中转服务里换原始密钥
                              中转密钥不变 ⇒ 所有工具配置一行都不用动
```

中转密钥是一个**稳定的间接层**，它把「上游密钥的生命周期」与「下游工具的配置」彻底解耦。上游可以随意更换、轮换、甚至换成另一个账号，下游完全感知不到。

**由此推出的第二个精髓**：中转服务转发每一次请求时，天然知道这一笔调用属于哪把中转密钥。因此用量统计**不再受制于上游平台的接口能力**——V2 中「DeepSeek 不支持按密钥统计」的问题，中转一上就彻底解决，且能拿到真正的逐笔明细而非周期聚合。

#### V1/V2 的「一工具一密钥」是中转的降级替代

必须记录清楚，否则日后容易误判「V2 已解决问题、V3 没必要」：

| 好处 | V1/V2（平台原生多密钥） | V3（中转） |
|------|:---:|:---:|
| 一工具一密钥的隔离 | ✅ | ✅ |
| 泄露后可单独作废 | ✅ | ✅ |
| **上游轮换不动下游配置** | ❌ **做不到** | ✅ |
| 按密钥/按工具的用量 | ⚠️ 受平台能力限制，DeepSeek 完全不支持 | ✅ 完全自主 |
| 逐笔明细 | ❌ | ✅ |
| 不需要服务端 | ✅ | ❌ |
| 请求内容不经第三方 | ✅ | ❌ **prompt 会流经中转** |

**V1/V2 期间的架构要求**：预留「凭证来源」与「用量来源」两个抽象扩展点，使 V3 成为增量新增而非重写。详见 FR-030、FR-031、[data-model.md](./data-model.md) §10。

#### 中转密钥的字符串格式（DC-015）

中转密钥 MUST 采用「**用户自定义前缀 + 分隔符 + 系统生成的随机后缀**」的形式，例如 `vscode-8f3a…`、`opencode_k29d…`。

- 前缀由用户自定义（通常填工具名），用于**肉眼识别这把密钥给了谁**。
- 后缀 MUST 由系统生成且具备足够随机性，**MUST NOT 允许用户自定义后缀**——用户自选字符串的熵不足，会显著降低密钥强度。
- 分隔符 MAY 为 `-` 或 `_`。

**连带重难点**：部分使用方工具的配置界面会校验密钥格式（如要求 `sk-` 开头）。前缀方案 MUST 在 V3 实测各主流工具的兼容性，必要时提供「兼容格式」选项（如 `sk-{前缀}-{随机}`）。

**重难点**：技术栈扩张到 JS/TS、重大隐私变更、部署体验、多平台协议适配、密钥双存储一致性、延迟与配额、审核风险。逐条见 [ROADMAP.md](../ROADMAP.md) V3 节。

**Independent Test**: V1/V2 不适用（未实现）。

### Edge Cases

- **生物识别不可用**（未录入、硬件不支持、连续失败被锁）：必须提供设备密码等等价确认方式，不得使用户永久无法访问自己的密钥。
- **剪贴板的系统级可见性**：iOS 会向用户提示粘贴行为，且其他 App 可能读取剪贴板。产品须在相关设置处说明此风险，不得暗示「复制」是绝对安全的通道。
- **通用剪贴板（Universal Clipboard）**：同一 iCloud 账号下，iPhone 上复制的内容可能被系统自动同步到附近的 Mac。这对「手机复制、电脑粘贴」是便利，但同时是明文离开本机的一条路径，须在设置处披露；若产品提供「仅本机剪贴板」选项，其实际行为须与文案一致。
- **多设备明文同步的连带影响**：明文经系统钥匙串同步后，任一台设备上的身份确认门闩仍须独立生效——在 B 设备查看明文同样要过 Face ID，不得因「已在 A 设备确认过」而放行。
- **延时清除剪贴板的边界**：若用户在清除生效前已复制了其他内容，不得清除用户的新内容；若 App 被系统终止，不得残留无法清除的明文（须说明该情形下的行为）。
- **高权限凭证的风险**：用于密钥管理与统计的管理类凭证权限大于普通密钥（可创建密钥、可产生消费）。须与普通密钥同等或更严格保护，并在配置处明确披露。
- **平台侧与本地状态不一致**：用户在平台官网删除了某把密钥，本产品仍有记录。刷新时须能识别并标注为「已失效」，不得继续呈现为可用。
- **录入时被输入法破坏的密钥**：iOS 的智能标点会把 `-` 替换为 `–`，自动大写会改掉首字母，粘贴时可能带进首尾空白或换行。这类密钥在保险库里看起来完好，实际发不出请求，而用户三个月后完全无法回溯原因。这是「密钥不能用」的**头号成因**，须在录入环节挡住，而不是等检测发现。
- **「未检测」「无法确认」「已失效」是三件事**：从未检测过的密钥不得带失效标记；因限流、断网、平台未接入而无法判定的，不得记为失效，且须保留上一次的结论与时间。把三者压成两态（能用 / 不能用）会产生大量虚假告警。
- **批量检测自伤**：并发或高频地检测同一账号下的多把密钥，会触发上游限流，进而把自己所有密钥判成失效。检测须串行并节流。
- **检测通过不等于可用**：探测端点返回成功只说明凭证被接受，不代表余额充足、不代表有权调用目标模型。文案须限定在「密钥有效」。
- **同一把密钥被录入两次**：会产生两条独立记录，V2 的用量随之被重复计算。须在录入时提示可能重复，但**不得为此存储明文的哈希**（宪法 VII）。
- **多设备的偏好冲突**：外观与默认视角这类设备相关偏好若随 iCloud 同步，会出现「在 Mac 上改深色导致 iPhone 也变深色」这种用户并不想要的联动；而验证方式、剪贴板时长这类安全设置则相反，必须各设备一致。二者须分开存放。
- **后台刷新不可靠**：系统对后台刷新的调度是机会性的，无法保证时效。所有基于后台刷新的提醒（余额不足、密钥失效、每周摘要）文案不得承诺实时。
- **平台能力差异导致的功能不齐**：同一界面下不同平台可用能力不同（能否 App 内建密钥、能否按密钥统计）。差异必须在界面上显式说明，禁止呈现为「功能故障」或「数据为零」。
- **免费额度边界**：达上限后删除一把应允许再次新增；权益失效后超额部分只读保留。
- **无网络**：保管、查看明文、复制、分配归属、查看历史统计快照等本地能力必须全部可用；仅「刷新用量」「App 内建密钥」等需要联网的操作降级并给出原因。
- **导出文件的安全性**：加密导出物在未掌握口令前不得被读出敏感明文；导入时须校验完整性并对版本不兼容给出可读提示。

## Requirements *(mandatory)*

### Functional Requirements

> **每条需求以 `[V1]` / `[V2]` / `[V3]` / `[跨阶段]` 标注所属阶段。** 编号保持稳定，
> 不因阶段划分而重排——下游文档（data-model / contracts / plan / tasks / quickstart）
> 大量引用这些编号，重排会造成引用漂移。

- **FR-001** `[V1]`: 用户 MUST 能够新增密钥，并为其设置名称、所属上游平台、密钥内容，以及可选的使用方工具与备注。
- **FR-002** `[V1]`: 系统 MUST 默认以掩码展示密钥，列表与详情页均 MUST NOT 直接呈现完整明文。
- **FR-003** `[V1]`: 「取出密钥明文」——**查看明文与复制到剪贴板共用同一门闩**——前，系统 MUST 按用户设定的验证方式完成身份确认。验证方式 MUST 提供四档：生物识别或设备密码（默认）、仅生物识别、应用专属主密码、不验证。设备不具备生物识别能力时「仅生物识别」MUST 不可选并说明原因；未设置主密码时「应用专属主密码」MUST 不可选。系统 MUST NOT 为查看与复制设置两个独立开关（二者产出同一份明文，分设开关会使门闩可被绕过）。
- **FR-003a** `[V1]`: 验证方式的文案 MUST 依设备实际硬件动态显示，并 MUST 使用 Apple 官方译名（中文为「面容 ID」/「触控 ID」，英文为 Face ID / Touch ID）；MUST NOT 自行翻译为「面容识别」「指纹识别」等非官方说法，MUST NOT 把两者并列为用户可选项——具体生物识别类型由设备硬件决定，用户无法选择。
- **FR-004** `[V1]`: 用户 MUST 能够将密钥明文复制到剪贴板，且 MUST 能选择是否禁用通用剪贴板（阻止内容经系统同步到其他设备）。
- **FR-005** `[V1]`: 系统 MUST 支持在用户设定的时长后自动清除由本产品写入剪贴板的密钥内容；可选时长 MUST 包含 2 分钟，且 MUST NOT 清除用户此后复制的其他内容。若平台能力无法保证清除必然执行（如应用已被系统终止），系统 MUST 降级为尽力而为并在设置处如实说明该局限，MUST NOT 隐瞒或暗示清除为绝对保证。
- **FR-006** `[V1]`: 用户 MUST 能够删除密钥。默认删除 MUST 将密钥移入「最近删除」回收站（保留 **30 天**），而非立即销毁明文——对齐系统「密码」App 的行为（DC-029）。回收站期间：主列表 MUST NOT 展示该密钥；免费额度 MUST NOT 计入；Keychain 明文 MUST 保留以支持恢复；指派关系 MUST 保留。用户 MUST 能在回收站内**恢复**或**立即永久删除**。满 30 天或立即永久删除后，系统 MUST 删除对应 Keychain 条目且不可再恢复，但其历史用量记录 MUST 保留并标注归属已删除。「清除全部数据」（FR-061）MUST 跳过回收站、立即永久清除（含回收站内条目）。进入回收站、恢复、立即永久删除 MUST 经不可关闭的身份确认（`confirmMandatory`）。
- **FR-007** `[V1]`: 用户 MUST 能够为每把密钥指定使用方工具，且**一把密钥 MUST 支持同时指派给多个使用方工具**（多对多）。指派与取消指派 MUST 可独立操作，取消对某个工具的指派 MUST NOT 影响该密钥对其他工具的指派。
- **FR-007a** `[V1]`: **上游平台与使用方工具两类都 MUST 支持用户自定义添加**。系统 MUST 内置常见项作为预置清单（上游平台至少覆盖 OpenAI、Claude、Google、OpenRouter、DeepSeek、阿里百炼、火山引擎、硅基流动；使用方工具见 CL-003）；用户 MUST 能添加任何未预置的项，自定义上游平台 MUST 支持填写自定义接入地址。预置项 MUST 可重命名或隐藏但 MUST NOT 可物理删除（应用更新会重新引入）；应用更新扩充预置清单时 MUST NOT 覆盖或删除用户自建项。
- **FR-008** `[V1]`: 系统 MUST 同时提供「按上游平台」与「按使用方工具」两种分组视角，展示同一份密钥数据；未指派给任何使用方的密钥 MUST 归入明确的「未分配」分组而非被隐藏。
- **FR-008a** `[V2]`: 因上游平台仅按密钥提供用量、无法拆分同一把密钥在不同工具间的消耗，**按使用方维度汇总时**：独占密钥（仅指派给 1 个工具）全额归入该工具；**共享密钥（指派给 ≥2 个工具）MUST 归入独立的「共享密钥」小计项并说明原因，MUST NOT 按任何比例摊分到各工具，也 MUST NOT 重复计入每个工具**。列表视图中共享密钥 MAY 同时显示在多个工具下，但汇总计算 MUST 只计一次。
- **FR-009** `[V2]`: 对支持密钥管理接口的平台，用户 MUST 能在产品内创建密钥（含命名与可选消费上限）、禁用与删除，且结果 MUST 与平台侧一致。
- **FR-010** `[V2]`: 当平台仅在创建时返回一次密钥明文而本地保存失败时，系统 MUST 明确告知用户平台侧已创建但本地未保存，并指引其前往平台处理；MUST NOT 静默丢失。
- **FR-011** `[V2]`: 对不支持密钥管理接口的平台，系统 MUST 明确说明需前往官网创建，MUST NOT 提供看似可用但必然失败的入口。
- **FR-012** `[V2]`: 系统 MUST 支持配置管理类凭证以启用密钥管理与用量统计；该凭证 MUST 受与普通密钥同等或更严格的保护，且配置处 MUST 明确披露其权限范围与风险。
- **FR-013** `[V2]`: 管理类凭证 MUST 为可选项；未配置时产品的保管、分配、双视角查看能力 MUST 完全不受影响。
- **FR-014** `[V2]`: 系统 MUST 在平台能力允许时展示每把密钥的用量，并 MUST 提供「按上游平台」与「按使用方」两个维度的汇总；汇总值 MUST 与其下各密钥之和自洽。
- **FR-015** `[V2]`: 当平台仅提供 token 数不提供按密钥费用时，系统 MUST 依据可追溯的单价规则估算费用，并 MUST 标明估算口径；MUST NOT 呈现为平台官方账单数字。
- **FR-016** `[V2]`: 当平台不支持按密钥拆分用量时，系统 MUST 在密钥级明确标注该平台能力限制，并在可获得时展示账户级余额；MUST NOT 留空或显示为零。
- **FR-017** `[V2]`: 刷新失败、无网络或平台接口变更时，系统 MUST 展示上次成功获取的数据及其时间戳，MUST 给出可读的失败原因，且本地数据 MUST NOT 丢失。
- **FR-018** `[V2]`: 单个平台的统计失效 MUST NOT 影响其他平台的统计或产品其他功能。
- **FR-019** `[V2]`: 单价规则变更后，历史已展示的估算值 MUST NOT 被静默改写；MUST 保留当时估算值或提供可追溯的口径说明。
- **FR-019a** `[V2]`: 用量周期的**时区口径 MUST 随每条用量数据一并记录并在界面标注**（如「按 OpenAI 口径 / UTC」）。各上游平台的周期口径不同（OpenAI 按 UTC 分桶，DeepSeek 按北京时间出账），若不记录口径，用户看到的「今天」会与平台后台不一致而误判产品统计有误；而 FR-019 禁止静默改写历史，事后统一口径将无法在不违反 FR-019 的前提下完成。**承载口径的字段 MUST 自 V1 起就存在于数据模型**（CloudKit 生产 schema 在 V1 一次性部署）。
- **FR-020** `[V2]`: 系统 MUST 能识别平台侧已被删除或失效的密钥并标注，MUST NOT 继续呈现为可用。
- **FR-021** `[V1]`: 系统 MUST 提供以下安全与偏好设置，且变更 MUST 立即生效并在重启后保持：打开 App 需要身份确认、**取出密钥明文的验证方式**（四档，见 FR-003）、应用专属主密码的设置与修改、自动清除剪贴板及时长（档位含 2 分钟）、**禁用通用剪贴板**、在应用切换器中隐藏、自动锁定时长、外观（浅色/深色/跟随系统）、默认启动分组视角、**清除全部数据**（见 FR-061）。
- **FR-021b** `[V2]`: V2 MUST 在设置中追加：**用量自动刷新间隔**、手动刷新用量、货币显示与汇率、单价规则管理、余额不足提醒、密钥失效提醒、每周摘要。
- **FR-021a** `[V2]`: 用量与余额的刷新 MUST 为自动执行且 MUST NOT 要求任何身份验证；刷新间隔 MUST 可由用户设定（建议档位：15 分钟 / 1 小时 / 6 小时 / 每天 / 仅手动）。应用在前台时 MUST 按设定间隔执行；应用在后台时受系统调度限制，MUST NOT 向用户承诺按设定间隔执行，设置项说明 MUST 明确这一区别。
- **FR-022** `[V1]`: 系统 MUST 支持受口令保护的加密导出与导入；导出物在未掌握口令时 MUST NOT 可被读出敏感明文；导入 MUST 校验完整性并对不兼容版本给出可读提示。**加密格式 MUST 自 V1 起就包含「用途标记」字段（完整备份 / 传递）与「导出范围」描述**，使 V2 的加密传递（FR-047）成为该格式的一种用途而非格式变更——否则 V2 会被迫做破坏性的格式升级，已导出的备份文件将无法被新版本正确识别用途。
- **FR-023** `[V2]`: 所有基于后台刷新的提醒文案 MUST NOT 承诺实时性，MUST 表述为在下次刷新时检查。
- **FR-024** `[V1]`: 系统 MUST 提供符合苹果审核要求的隐私说明，涵盖本产品对密钥与管理类凭证的处理方式、数据存放位置与不上传承诺。
- **FR-025** `[V1]`: 从主界面完成「新增一把密钥并指定使用方」的关键确认步数 MUST NOT 超过 3 步（不含系统权限弹窗与身份确认 sheet）。

#### 应用专属主密码（DC-007）

- **FR-036** `[V1]`: 系统 MUST 支持用户设置一个**独立于设备密码**的应用专属主密码，并可将其作为「取出密钥明文」的验证方式之一（FR-003 第三档）。主密码 MUST NOT 以明文或可逆形式存储；MUST 使用加盐的口令派生函数存储校验材料。
- **FR-037** `[V1]`: 系统 MUST 提供主密码的修改路径，且 MUST 提供**忘记主密码后的恢复路径**——经生物识别或设备密码确认后可重置主密码。设置主密码时 MUST 明确告知该恢复路径的存在，MUST NOT 让用户误以为主密码是不可绕过的最强保护。
- **FR-038** `[V1]`: 主密码的校验材料 MUST NOT 经 iCloud 同步（否则一台设备上的重置会影响其他设备的预期）；每台设备的主密码独立设置。该行为 MUST 在设置处说明。

#### 加密传递（DC-016）

- **FR-047** `[V2]`: 用户 MUST 能够勾选若干密钥生成受口令保护的加密文件用于交付他人。该能力 MUST 复用 FR-022 的加密格式，并 MUST 在格式中标记用途（完整备份 / 传递），使导入方据此呈现相应告知。
- **FR-048** `[V2]`: 加密文件 MUST 经**系统分享面板**交付，MUST NOT 经过本产品或开发者的任何服务器，MUST NOT 生成托管型下载链接。
- **FR-049** `[V2]`: 传递流程 MUST 展示不可忽略且如实的告知：**传出后无法撤回**；**对方产生的消费记在传出方账上**；**多数上游平台的服务条款禁止将密钥分享给第三方**。系统 MUST NOT 提供任何「撤回」入口——技术上不存在，提供即为虚假承诺（宪法 IX）。
- **FR-050** `[V2]`: 本能力 MUST 命名为「加密传递」，MUST NOT 使用「共享」「协作」等暗示可管控的措辞——可撤销的共享属 V3 的中转能力（US7）。导入的密钥 MUST 标注来源为「他人传递」。

#### 本地化与全球上架（DC-014）

- **FR-042** `[V1]`: 界面语言 MUST 覆盖**英语与简体中文两种**。**开发语言 MUST 为英语**——App Store 与系统在用户语言未被覆盖时回退到开发语言，若以中文为开发语言，非中文用户将看到中文界面。
- **FR-043** `[V1]`: 界面字符串 MUST 使用语义化 key 管理，MUST NOT 以英文原文作为 key（修改原文等于更换 key，会静默丢失已有中文翻译）。MUST NOT 硬编码任何面向用户的字符串。日期、数字、货币 MUST 按用户区域设置格式化。Apple 专有名词 MUST 使用官方译名（「面容 ID」「触控 ID」「钥匙串」）。
- **FR-044** `[V1]`: **隐私政策与法律文本 MUST 由人工提供英语与简体中文两个版本，MUST NOT 使用机器翻译**——法律文本的机翻错误直接构成合规风险。商店元数据（描述、关键词）MAY 对其余语言使用机器翻译。
- **FR-045** `[V1]`: 因产品使用加密算法（AES-GCM 加密备份、PBKDF2 主密码派生），`Info.plist` MUST 正确声明 `ITSAppUsesNonExemptEncryption`，并按需准备出口合规材料。**这是全球上架的实际卡点，遗漏会在提交阶段被阻断。**
- **FR-046** `[V1]`: 用户输入的内容（密钥名称、自定义平台名、自定义工具名）MUST NOT 被本地化或翻译，MUST 原样保存与呈现。

#### 上架合规的工程卡点（DC-018）

- **FR-058** `[V1]`: 工程 MUST 包含 `PrivacyInfo.xcprivacy` 隐私清单，并如实声明所使用的、需要说明理由的 API 类别（至少包含 `UserDefaults`，理由码 `CA92.1`）与数据收集情况。**这与 FR-045 的加密出口声明是同一类「提交阶段才暴露的硬卡点」**，缺失或理由不当会在上传时被阻断。隐私清单是**工程文件而非商店材料**，故 MUST 在 V1 完成。商店侧元数据/问卷/截图亦随 Stage1→**1.0.0** 准备（DC-013 已废止，不得再推迟到 V2）。

#### 无障碍（DC-024）

- **FR-059** `[V1]`: 全部界面 MUST 支持 Dynamic Type，MUST NOT 依赖固定字号或固定高度容纳文本。失效等状态标记 MUST NOT 仅依赖颜色传达。密钥明文的朗读规则：**掩码位 MUST NOT 被读出完整明文**；通过门闩后的明文展示区 MAY 被读出，且 MUST 支持**逐字符朗读**。MUST NOT 一概禁止 VoiceOver 读出明文——那会使视障用户完全无法使用本产品。

#### 偏好的同步边界（DC-021）

- **FR-060** `[V1]`: 偏好设置 MUST 分为两组分别存放：**安全相关偏好**（取出明文的验证方式、App 锁、自动锁定时长、剪贴板清除时长、禁用通用剪贴板、在应用切换器中隐藏）MUST 在用户的各设备间保持一致并随用户数据同步；**设备相关偏好**（外观、默认启动分组视角、窗口尺寸）MUST 仅存于本机、MUST NOT 同步。理由：安全策略在各设备上应一致，而外观与默认视角是设备各自的选择，同步它会造成用户并不想要的联动。

#### 密钥可用性检测（DC-017）

- **FR-051** `[V2]`: 用户 MUST 能手动检测密钥是否仍被上游平台接受，粒度 MUST 包含**单把密钥**与**当前列表全部密钥**两种。批量检测 MUST 串行执行并节流，同一把密钥在冷却期内 MUST NOT 被重复检测。系统 **MUST NOT** 在启动、进入前台或任何后台时机自动执行检测。
- **FR-052** `[V2]`: 检测结果 MUST 区分四种状态并分别呈现：**未检测**（无任何标记，MUST NOT 显示失效标记）、**有效**、**已失效**、**未能确认**。429（限流）、超时、5xx、无网络 MUST 归入「未能确认」，**MUST NOT 判为已失效**，且 MUST 保留上一次的结论与其时间戳（宪法 IX）。已失效的密钥 MUST 在两种分组视角的列表中都带醒目标记，且该标记 MUST NOT 仅依赖颜色区分。
- **FR-053** `[V2]`: 检测 **MUST NOT 触发身份确认门闩**——明文未交付给用户，且批量检测逐次弹出生物识别会使功能不可用。读取明文用于检测的路径 MUST 以显式命名体现（宪法 VIII）。
- **FR-054** `[V2]`: 检测结果的文案 MUST 限定为「密钥有效」，**MUST NOT 表述为「可用」**——余额、配额与模型权限均未被检查。对系统不知道检测端点的平台（含用户自定义平台），MUST 说明「该平台未接入检测」并保持「未检测」状态，MUST NOT 显示失效标记。
- **FR-055** `[跨阶段]`: 密钥的**健康度**MUST 是独立于生命周期状态（`active` / 平台侧已作废 / 已删除）的一组字段，MUST NOT 复用生命周期字段承载检测结果——二者来源与置信度不同（检测得到的 401 只说明「当前不被接受」，而生命周期的「平台侧已作废」是经管理凭证对账确认的事实）。健康度字段 MUST 自 V1 起就存在于数据模型并随用户数据同步（密钥失效是平台侧的客观事实，一台设备检测出来其他设备也应看到），V1 不写入任何非「未检测」的值。

#### 密钥录入的正确性（DC-025）

- **FR-056** `[V1]`: 密钥录入控件 MUST 关闭自动更正、自动大写与智能标点/智能引号；录入内容 MUST 去除首尾空白，MUST 拒绝包含空格、制表符或换行的内容并说明原因。长度明显异常时 MUST 给出提醒但 MUST NOT 阻止保存（各平台格式不一，硬校验会挡住合法密钥）。
- **FR-057** `[V1]`: 新增密钥时，若同一上游平台下已存在**末 4 位与字符长度都相同**的密钥，系统 MUST 提示可能重复并指出是哪一条，由用户确认后继续。系统 **MUST NOT** 为此存储密钥明文的哈希或任何其他派生物（宪法 VII）。

#### 关系图（DC-008）

- **FR-039** `[V2]`: 系统 MUST 提供「平台账号 — 密钥 — 使用方工具」三列关系图；节点与连线 MUST 反映当前真实指派关系，未指派密钥 MUST 连向明确的「未分配」节点。
- **FR-040** `[V2]`: 关系图 MUST 支持点击节点高亮其全部关联路径。有用量数据时连线粗细 MUST 映射用量金额；无法统计用量的平台其连线 MUST 以明确样式区分并说明原因，MUST NOT 呈现为「用量为零」。
- **FR-041** `[V2]`: 关系图以 Mac 为主要目标平台。在 iPhone 上 MUST 提供可读的降级形态或明确的「请在 Mac 上查看」提示，MUST NOT 呈现为无法辨认的重叠图形。

#### 付费边界

- **FR-026** `[V1]`: 免费用户 MUST 最多保存 3 把密钥；达上限时 MUST 拒绝新增并说明升级可解锁无限密钥。
- **FR-027** `[V1]`: 已购用户 MUST 解除密钥数量上限；除数量外，免费态与已购态的功能范围 MUST 一致。
- **FR-028** `[V1]`: 系统 MUST 提供「恢复购买」，使用户在更换设备或重装后可恢复权益。
- **FR-029** `[V1]`: 权益失效后，超出免费额度的密钥 MUST 只读保留（可查看、可复制、可删除），仅新增受限；MUST NOT 强制删除或隐藏用户数据。
- **FR-061** `[V1]`: 系统 MUST 提供「清除全部数据」，用于清除本产品写入的全部用户数据：全部 Keychain 条目（含普通密钥、管理类凭证、本机主密码校验材料、**回收站内尚未到期的密钥**）、SwiftData/CloudKit 中的用户实体、本机 `RefreshHealth` 与设备偏好。执行前 MUST 经不可关闭的身份确认（`confirmMandatory`），MUST 二次确认并如实告知「不可撤销；跳过 30 天回收站；若开启 iCloud 同步，其他设备上的对应同步数据也会被清除」。系统 **MUST NOT** 清除或吊销 StoreKit 已购权益（权益真相源仍是 App Store；本地权益快照可清，用户可「恢复购买」）。系统 MUST 在流程中建议用户先加密备份（FR-022），MUST NOT 把清除伪装成「退出登录」（本产品无账号体系）。

- **FR-062** `[V1]`: 内购的商店配置含不可逆项，MUST 在首次提交前定稿：**家庭共享一旦为某内购开启即不可关闭**（本产品为一次性买断，倾向开启）；产品 ID 创建后不可删除、不可复用，故 MUST 一次性约定命名规则并为 V3 的第二档预留。V3 的第二档 MUST 是**独立的非消耗型内购**，MUST NOT 将买断改为订阅（已购用户的权益处理无法做到既合规又不惹恼用户）。

- **FR-063** `[V1]`: CloudKit **生产环境（Production）schema** MUST 在 Phase 2 Checkpoint 通过前完成部署，且部署内容 MUST 覆盖 data-model 定义的全部同步实体与字段（含仅 V2 写入的健康度等预留字段）。Development 环境可见不等于 Production 已就绪——遗漏会导致 TestFlight / 正式包用户同步失败或静默丢字段。此后对生产 schema 的变更 MUST 仅 additive（宪法 VI、宪法「不可逆决策」）。

#### 跨阶段架构扩展点（V1 即须满足，否则 V2/V3 会被迫重写）

- **FR-030** `[跨阶段]`: 系统 MUST 将「凭证来源」定义为可扩展抽象，V1 仅实现「用户录入的真实密钥」一种来源，使后续新增「平台签发」（V2）与「中转签发」（V3）不需要改动界面层与既有数据结构语义。
- **FR-031** `[跨阶段]`: 系统 MUST 将「用量来源」定义为可扩展抽象，且用量数据结构 MUST 同时容纳「周期聚合值」与「逐笔明细」两种形态，避免 V3 接入逐笔明细时发生破坏性数据迁移。
- **FR-032** `[跨阶段]`: 权益模型 MUST 按三级设计（免费 / 无限密钥 / 中转），V1 与 V2 仅前两级可达；第三级 MUST NOT 出现在 V1/V2 的付费界面中。

#### 平台与同步范围

- **FR-033** `[V1]`: 密钥明文 MUST 通过系统钥匙串在用户本人的 Apple 设备之间同步；产品内与上架材料的隐私表述 MUST 与该行为一致，MUST NOT 声称明文永不离开本机。
- **FR-034** `[V1]`: V1 MUST 同时交付 iPhone 与 Mac；业务能力两端一致，界面 MUST 按各平台的系统设计规范适配。
- **FR-035** `[V1]`: 在 V1 与 V2，产品 MUST NOT 与任何外部工具建立集成（读写其配置、代为填充、插件或扩展）；密钥交付终点 MUST 为系统剪贴板。V3 的中转服务不改变这一点——工具仍由用户自行配置，只是配置的内容从原始密钥换成中转密钥。

### Out of Scope

以下条目**不属于**本 Feature，不进入 plan/tasks 拆解：

- **FR-OUT-001**: App 内的 AI 聊天或调用窗口。本产品不做对话客户端。
- **FR-OUT-002**: 自建中转服务及其部署流程（阶段三，见 US7）。
- **FR-OUT-003**: 自定义密钥字符串。依赖中转，属阶段三。
- **FR-OUT-004**: 系统级 AutoFill Credential Provider Extension（向其他 App 提供凭证填充）。
- **FR-OUT-005**: 网页端数据看板；团队协作与组织账号。
- **FR-OUT-006**: 对平台官网后台的网页抓取或模拟登录（如导出 CSV 账单）。仅使用平台公开接口。
- **FR-OUT-007**: 与外部工具的任何形式集成——读写其配置文件、代为填充、插件或扩展。密钥交付终点为系统剪贴板。

本规范不讨论具体技术实现方式、架构选型、接口设计、存储方案与代码结构——这些属于 plan.md 与 research.md 的职责范围。

### Key Entities *(include if feature involves data)*

- **上游平台账号**：用户在某个 **API 提供方**的账号上下文；含平台标识（预置或用户自定义）、可选的自定义接入地址、可选的管理类凭证；决定该平台下可用的能力（能否 App 内建密钥、能否按密钥统计）。同一平台允许多个账号。
- **密钥**：一条访问凭证；含名称、所属上游平台、创建时间、状态（可用 / 平台侧已失效 / 已删除）、来源（用户录入 / 平台签发 / 中转签发）；明文受身份确认保护；受免费数量上限约束。
- **密钥健康度**：某把密钥最近一次**主动检测**的结果，含状态（未检测 / 有效 / 已失效 / 未能确认）、检测时间与不可判定时的可读原因。它**独立于上面的「状态」字段**：健康度来自用密钥自己发起的探测，而「平台侧已失效」来自经管理凭证的对账，二者置信度不同（见 FR-055）。
- **使用方工具**：消费密钥的**客户端软件**（如 VS Code、Cursor、OpenCode、Trae）；含名称与可选图标；一个使用方可持有跨多个上游平台的多把密钥。
- **指派关系**：密钥与使用方工具之间的**多对多**关联。一把密钥可同时指派给多个工具（此时称为「共享密钥」，其用量无法归属到单个工具，见 FR-008a）；未有任何指派的密钥归入「未分配」。
- **用量数据**：某把密钥在某时间范围内的消耗；可为周期聚合值（日/周/月/累计）或逐笔明细（阶段三）；含 token 数、费用（可能为估算）、获取时间戳与数据来源标识。
- **余额**：某上游平台账号的账户级剩余额度；在平台提供时可用。
- **单价规则**：用于在平台仅提供 token 数时估算费用的口径；含模型匹配、输入输出单价、生效日与来源。
- **权益状态**：用户当前处于免费 / 无限密钥 / 中转（本期不可达）三级中的哪一级；决定密钥数量上限。
- **偏好设置**：用户的安全与外观选择；影响身份确认时机、剪贴板行为、界面呈现与提醒开关。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新用户从打开产品到完成「保存首把密钥并指定使用方」不超过 3 个关键操作步骤。验收口径：干净安装状态下自测 5 次，5 次均 ≤3 步且无阻塞性错误。
- **SC-002**: 查看或复制密钥明文的路径上，100% 的请求在明文暴露前完成身份确认；取消或失败时 0 次明文泄露。验收口径：对查看与复制两条路径各人工验证 10 次。
- **SC-003**: 由本产品写入剪贴板的密钥，在设定时长到达且进程仍存活时 100% 被清除；且 0 次误清用户此后复制的其他内容。**例外（与 FR-005 一致）**：App 在过期前被系统终止时，清除可能无法执行——属平台限制，须在产品/上架材料中如实披露，不得在本 SC 中写成绝对保证。
- **SC-004**: 免费用户新增第 4 把密钥时 100% 被拦截并看到升级说明；已购用户新增第 4 把及以上 100% 成功；权益失效后超额密钥 0 条被删除或隐藏。
- **SC-005**: 在支持按密钥统计的上游平台上，两个维度的汇总值 100% 自洽。口径为：`按使用方维度总量（独占密钥之和 + 共享密钥小计 + 未分配小计）` **等于** `按平台维度总量（各密钥之和）`。共享密钥 0 次被摊分、0 次被重复计入。验收口径：构造「一把密钥指派给 2 个工具」的场景核对，并随机抽取 3 个上游平台各核对一次。
- **SC-006**: 对不支持按密钥统计的平台，100% 在密钥级显示能力说明文案，0 处留空或显示为零。
- **SC-007**: 断网或平台接口失败时，100% 展示上次数据及其时间戳并给出可读原因，本机数据 0 丢失；单平台失效 0 次影响其他平台或其他功能。
- **SC-008**: 在 App 内创建密钥的平台上，创建成功后平台侧与本地状态 100% 一致；发生「平台已建但本地未存」时 100% 给出明确指引，0 次静默丢失。
- **SC-009**: 加密导出物在无口令时 0 次可读出敏感明文；正确口令导入后保险库内容 100% 可恢复。
- **SC-010**: 上架材料与产品内包含可访问的隐私说明，明确交代密钥与管理类凭证的处理方式；审核反馈中无因缺失披露导致的拒审。
- **SC-011**: 密钥可用性检测的误判为零。验收口径：构造四种情形各验证一次——有效密钥、平台侧已删除的密钥、断网、人为触发 429。要求：**0 次**把断网或 429 判为「已失效」；**0 处**给从未检测过的密钥显示失效标记；无法判定时 **100%** 保留上一次结论与其时间戳。
- **SC-012**: 密钥录入的规范化 100% 生效。验收口径：在开启智能标点与自动大写的输入环境下粘贴与手输各 3 次含 `-` 的密钥，要求 **0 次**出现字符被替换或大小写被改动；带首尾空白或换行的粘贴内容 **100%** 被规范化或明确拒绝。
- **SC-013**: 设备相关偏好 0 次跨设备同步，安全相关偏好 100% 跨设备一致。验收口径：在两台设备上分别改动外观与验证方式，核对同步行为符合 FR-060。
- **SC-014**: 「清除全部数据」后，本机 Keychain 与 SwiftData 中本产品用户数据 100% 不可再读出；StoreKit 已购权益 100% 仍可通过「恢复购买」恢复。验收口径：清除前后各核对一次密钥列表、Keychain 条目数与恢复购买路径。
- **SC-015**: 删除→回收站→恢复路径 100% 可逆（明文与指派均恢复）；满 30 天或「立即删除」后 100% 不可再取出明文。验收口径：删除后 0 次出现在主列表且额度已释放；恢复后可复制；将 `deletedAt` 拨到 31 天前触发清理后 Keychain 无对应条目。

## Assumptions

- 目标用户为苹果生态下的 AI 开发者与重度 AI 工具使用者，具备基本的 API 使用经验（知道什么是 API 密钥、会在开发工具中配置它）。
- 目标平台首批覆盖 DeepSeek、OpenAI、Claude、OpenRouter，并预留扩展其他主流平台的能力。
- **平台能力差异是既定事实而非缺陷**：经调研，OpenRouter 支持在产品内创建密钥并按密钥读取用量；OpenAI 与 Claude 在配置管理类凭证后可按密钥读取 token 用量（费用需自行按单价估算）；DeepSeek 仅提供账户级余额，不支持按密钥拆分。产品的职责是把差异如实呈现给用户，而不是掩盖或假装齐平。
- 用量与余额数据的**唯一真相源是各平台**；本产品只做读取、归集与展示，不产生权威账单数字。因此展示的费用在多数情况下为估算，须明确标注口径。
- 阶段一的「一工具一密钥」依赖上游平台原生支持多密钥。假定目标平台均允许同一账号创建多把密钥。
- 「绑定使用方」在阶段一是**记录性质**的，不具备强制力：本产品不介入 API 流量，无法阻止用户把同一把密钥用于其他工具，也无法检测该行为。此局限须在产品内如实说明，避免用户误解为安全保证。
- 免费额度 3 把是可调的商业参数，不是技术约束；调整不应引起架构变更。
- 密钥明文在用户本人的 Apple 设备之间通过系统钥匙串端到端加密同步。因此产品的隐私承诺是「仅在你本人的 Apple 设备之间同步」，而非「永不离开本机」；产品内文案与上架材料须与此一致。
- 本期同时交付 iPhone 与 Mac。业务与数据能力两端一致，界面按各平台系统规范分别适配。
- 产品不介入 API 流量，也不与外部工具集成；密钥的交付终点是系统剪贴板，粘贴由用户完成。
- 付费形态为一次性买断（非订阅），通过应用内购买实现，需支持恢复购买。
- 「操作不超过 3 步」计量主路径上的关键确认动作，不含系统权限弹窗与身份确认 sheet。
- 后台刷新依赖系统调度，不保证时效；相关提醒为「尽力而为」而非实时告警。
- 中转、自定义密钥字符串、网页端、团队协作均留待后续，不纳入本次验收。

## 已裁决事项

以下决策已由产品负责人裁决，作为 plan 的输入约束：

- **DC-001 多设备的密钥明文**：明文随系统钥匙串在**用户本人的 Apple 设备之间**同步（系统端到端加密）。因此隐私表述 MUST 为「仅在你本人的 Apple 设备之间同步」，MUST NOT 声称「永不离开本机」。见 FR-033。
- **DC-002 平台范围**：本期同时覆盖 iPhone 与 Mac。理由：核心动作是把密钥交给开发工具，而目标工具主要运行在 Mac 上；仅做 iPhone 会使主流程价值大幅折损。见 FR-034。
- **DC-003 剪贴板与自动清除**：允许写入剪贴板，清除时长可由用户配置，档位包含 2 分钟。若平台能力无法保证清除必然执行（如应用被系统终止），MUST 降级为「尽力而为」并在设置处如实说明，MUST NOT 因此移除该能力或隐瞒局限。见 FR-005。
- **DC-004 交付边界**：产品的职责终点是系统剪贴板，不与任何外部工具集成。见 FR-035、FR-OUT-007。
- **DC-005 中转的存放方向（V3）**：V3 的中转密钥与逐笔用量明细存放于**用户自有的 Cloudflare 账号**，不由本产品托管。V1/V2 不实现，仅按 FR-030 / FR-031 预留扩展点。
- **DC-006 门闩与刷新的分工**：
  - **取出密钥明文**（查看与复制**共用同一门闩**）需身份确认，验证方式由用户四档自选，含「不验证」。见 FR-003。
  - **用量与余额刷新**是自动的、按用户设定的间隔执行，**不需要任何身份验证**。见 FR-021a。
  - 连带的技术约束：经调研，Keychain 的 **iCloud 同步与系统级生物识别 ACL 互斥**（不可并存）。因 DC-001 要求同步、DC-002 要求 Mac 可用，门闩改为**应用层**实现。此方案弱于系统级强制，产品 MUST NOT 宣称「系统级强制」。详见 research.md §1。
  - 管理类高权限凭证的门闩 MUST NOT 可关闭，但自动刷新读取它时不触发门闩。
- **DC-007 应用专属主密码**：**做**。作为「取出密钥明文」验证方式的第三档，独立于设备密码。见 FR-036～FR-038。
  - 连带取舍：MUST 提供「忘记主密码」的恢复路径（经生物识别或设备密码重置），否则用户忘记后将永久失去全部密钥，构成数据丢失风险。这意味着主密码的实际安全强度**不高于**设备密码，MUST 在设置时如实告知（宪法 IX）。
  - 主密码校验材料 MUST NOT 经 iCloud 同步，每台设备独立设置。
- **DC-008 关系图的形态**：做**三列桑基式关系图**（平台 — 密钥 — 使用方），**不做自由布局的思维导图**。归入 V2。见 US8、FR-039～FR-041。
  - 理由：数据是三层分明的，「一把密钥属于多个平台」在技术上不存在；真正的多对多只有「平台 ↔ 使用方」这一层，经密钥间接连接。三列布局更易读，且不需要在无第三方库的前提下自研力导向布局算法。
- **DC-009 分三阶段实施**：V1 密钥保险库 / V2 用量看板与关系图 / V3 中转服务，每阶段独立分支、独立交付、**独立上架**（Stage N → App Store **N.0.0**）。**前一阶段未验收通过 MUST NOT 开始下一阶段实现。** 范围权威见 [ROADMAP.md](../ROADMAP.md)；分支命名见 [playbooks/BRANCHES.md](../playbooks/BRANCHES.md)。
- **DC-010 中转的精髓已更正**：中转的核心价值是**上游密钥轮换时下游工具配置完全不动**，以及**统计能力不再受制于上游平台接口**；「一把拆多把」只是次要好处。见 US7。
- **DC-011 指派关系为多对多**：一把密钥 MAY 同时指派给多个使用方工具。见 FR-007。
  - 连带代价（必须接受）：上游平台只按密钥提供用量，无法拆分同一把密钥在不同工具间的消耗。因此**共享密钥的用量无法归属到单个工具**，只能单列「共享密钥」小计。见 FR-008a。摊分或重复计数都会产生虚假数字，一律禁止（宪法 IX）。
  - **该限制只有 V3 的中转能解除**：中转可为同一把原始密钥向不同工具签发不同的中转密钥，逐笔归属自然清晰。这是中转价值的第三条论据。
- **DC-012 两类平台都支持自定义添加**：上游平台与使用方工具均为「内置预置 + 用户可自定义添加」。见 FR-007a、术语表。
- **DC-014 语言范围与全球上架**：界面只做**英语 + 简体中文**两种，其余语言不做界面本地化。产品面向**全球上架**。
  - **开发语言 MUST 为英语**——这是最容易搞错也最致命的一点。App Store 与系统在用户语言未被覆盖时回退到开发语言；若以中文为开发语言，一个法国用户会看到中文界面。
  - 字符串用**语义化 key**，不以英文原文作 key。否则改英文文案等于换 key，中文翻译会静默丢失——本项目处于持续迭代期，这个代价不可接受。
  - 隐私政策与法律文本 MUST 人工提供双语，MUST NOT 机翻；商店描述等元数据 MAY 对其余语言机翻。
  - 加密出口合规声明（`ITSAppUsesNonExemptEncryption`）MUST 处理，否则提交阶段被阻断。
  - 见 FR-042～FR-046、宪法 v2.1.0「本地化」节。
- **DC-015 中转密钥格式（V3）**：用户自定义前缀 + 分隔符 + **系统生成的随机后缀**。后缀 MUST NOT 允许用户自定义（熵不足会降低密钥强度）。见 US7。
- **DC-016 分享分两层实现**：
  - **V2「加密传递」**：勾选密钥生成口令加密文件，经系统分享面板交付，不经任何服务器。**不可撤回**，必须如实告知。复用加密备份格式，成本极低。见 US9、FR-047～050。
  - **V3「共享」**：为他人签发专属中转密钥，**可单独撤销、可单独统计、可设消费上限**，对方拿不到原始密钥。见 US7。
  - 两者 MUST 在命名上严格区分，MUST NOT 让「传递」使用暗示可管控的措辞。这样避免出现两套并存的分享机制与两种心智模型。
  - **不做团队功能**（成员管理、角色权限、审计日志）。理由：那需要服务端与账号体系，量级完全不同；而中转密钥已覆盖小团队的实际需求——给每人签发一把，谁用多少一目了然，谁离职撤谁的，不需要「团队」这层抽象。
  - **连带风险**：多数上游平台的服务条款禁止把 API 密钥分享给第三方（如 OpenAI）。产品 MUST 在流程中提示，MUST NOT 装作不知情；此项也可能在苹果审核时被问询。
- **DC-017 密钥可用性检测归 V2**：做，但**归入 V2**。见 US10、FR-051～FR-055。
  - 实现方式：用密钥自己向上游发起一次不消耗 token 的最小请求（`GET /v1/models` 一类），按返回码判定。**不需要管理类高权限凭证**——这是它与 US4 用量统计的关键差异，也是它在 DeepSeek 这类「不支持按密钥统计」的平台上依然可用的原因。
  - 归 V2 的理由：检测必然联网，而 V1 的定义性边界是完全不联网调上游。V1 以 1.0.0 单独上架；探活随 2.0.0 交付。同时保住 V1「零网络」带来的全部简化（无需 HTTPClient、无需网络权限、无需错误分类体系）。
  - **V1 唯一需要做的事**：在数据模型中预留健康度字段（FR-055）。因为 CloudKit 生产 schema 在 V1 一次性部署，漏了就要重新部署 schema。
  - 连带取舍（必须接受）：检测把密钥发往其所属上游平台。这本就是该密钥的去处，但产品 MUST 在功能处说明「检测会向该平台发起一次请求」，MUST NOT 让用户以为这是纯本地操作。
  - 门闩例外：检测 MUST NOT 触发门闩（FR-053），与「自动刷新读管理凭证不触发门闩」同一类例外，已写入宪法 VIII。
- **DC-018 四个工程标识符统一为 `com.apirelay.*` 并视为不可逆决策**：
  - 现状问题：工程实际 bundle id 为 `com.dsx.ApiRelay`，而文档中的 Keychain Service 为 `com.apirelay.keychain.*`、App Group 为 `group.com.apirelay.shared`，**两套前缀混用**。
  - 裁决：**统一到 `com.apirelay.*` 一套**，保持品牌一致。确切取值登记在 [plan.md](./plan.md) A5：
    Bundle `com.apirelay.ApiRelay`、容器 **`iCloud.com.apirelay.ApiRelay`**（废弃别名 `iCloud.com.apirelay.app`）、
    App Group `group.com.apirelay.shared`。
  - 为何列为不可逆：**Team ID 变更会改变 `$(AppIdentifierPrefix)`，使已存的全部 Keychain 条目读不出来**；`keychain-access-groups` 在有用户数据后同样不可改；App Group 与 iCloud 容器标识符在**全 Apple 生态唯一**，注册后不可改名，也存在被他人占用的风险。因此 MUST 在写第一行业务代码前定稿。见宪法「不可逆决策」节。
- **DC-019 Swift 6 语言模式 + 最低系统版本 iOS 18.0 / macOS 15.0**：
  - **Swift 语言模式定为 6**（工程现为 5.0，同时已开启 `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`）。理由：本项目大量跨 actor 传递（Keychain 与各平台适配器为 `actor`，界面在 `MainActor`），若先以 Swift 5 写完再切，严格并发检查会一次性产生大量 `Sendable` 错误。项目当前只有模板代码，是成本最低的切换时点。
  - **最低版本由 iOS 17.0 / macOS 14.0 提升为 iOS 18.0 / macOS 15.0**。理由：本项目重度依赖 SwiftData + CloudKit + 双 `ModelConfiguration`，该组合在 17.x 上的同步稳定性与 `#Predicate` 支持存在已知问题。上架后抬高版本会把已有用户挡在升级之外，因此**当前是唯一能自由选择的时点**。
- **DC-020 Mac 形态定为 Mac Catalyst，且理由必须被记录**：见 [research.md](./research.md) §3。
  - 硬论据：**原生 macOS 的 `NSPasteboard` 没有 `expirationDate` 的等价机制。** FR-005 要求的「应用被系统终止后剪贴板仍被清除」在原生 macOS 上做不到，只能退回应用内计时器，而应用一退出即失效。也就是说 Catalyst 不是省事的选择，而是 FR-005 在 Mac 上能够成立的前提。
  - 记录它的目的：防止日后有人为了「Mac 上更原生」把界面层迁到独立的 macOS target，顺手破坏 FR-005 且无人察觉。此项变更 MUST 视为 MAJOR。
- **DC-021 偏好拆分为「同步的安全设置」与「本机的界面偏好」**：见 FR-060。
  - 为何现在定：事后把字段从同步实体搬到本机实体是**跨 `ModelConfiguration` 的数据搬迁**，比新增字段麻烦得多。
- **DC-022 用量周期的时区口径随数据记录并在界面标注**：见 FR-019a。字段自 V1 起进入数据模型。
- **DC-023 内购的不可逆配置**：见 FR-062。定稿取值见 [plan.md](./plan.md) A5：
  - 产品 ID：`com.apirelay.iap.unlimited_keys`（V1）；预留 `com.apirelay.iap.relay`（V3，本期不创建）。
  - **家庭共享：开启**（一旦开启不可关闭）。
  - V3 第二档必须是独立的非消耗型内购，MUST NOT 把买断改为订阅。
- **DC-024 无障碍与明文朗读规则**：见 FR-059。
  - 本项修正了原 tasks.md T060 的一处方向性错误——「MUST NOT 让 VoiceOver 读出明文」会使视障用户完全无法使用本产品。安全边界应落在**门闩**上，而不是落在辅助功能上。
- **DC-025 密钥录入的正确性防护**：见 FR-056、FR-057。
  - 提出背景：在评估 US10 时识别到，**密钥失效的头号成因不是平台作废，而是录入时被输入法破坏**（智能标点把 `-` 换成 `–`、自动大写、粘贴带进换行）。这类密钥在保险库里看起来完好但发不出请求，且用户事后无法回溯原因。V1 拦住它的成本为零，漏掉的代价是 V2 上线后出现一批查不出原因的「已失效」。
  - 重复录入的检测 MUST NOT 依赖明文哈希（宪法 VII 禁止明文派生物进入同步存储），改用平台 + 末 4 位 + 长度的弱比对并由用户确认。
- **DC-013 上架时机**：**已废止**（编号保留，不得复用）。原「V1 不单独上架、与 V2 一并提交」已由产品负责人改回与 **DC-009** 一致：每阶段独立上架（Stage1→**1.0.0**，Stage2→**2.0.0**，Stage3→**3.0.0**）。
  - 现行要求：V1 仍须完成安全审查与付费逻辑；**App Store 元数据、隐私问卷、商店截图与提交审核在 Stage1 验收时准备**，不再推迟到 V2。
  - **V1 的付费逻辑不因上架节奏而省略**——它决定数据模型与权益判断，后补会引起返工。
- **DC-026 提供「清除全部数据」**：做，归 V1。见 FR-061、SC-014。
  - 理由：本产品无服务器账号，但持有最高敏感度的用户资产（API 密钥）。隐私问卷与审核常问「用户如何删除其数据」；没有明确入口会在问卷里被迫含糊其辞，也让想离手的用户只能卸载却清不掉 iCloud 钥匙串与 CloudKit 里的残留。
  - 连带取舍：开启同步时，清除会经由 iCloud 钥匙串 / CloudKit 传播到用户其他设备——这是正确行为（「删的是我的数据」），但 MUST 事前说清楚，MUST NOT 写成「仅清除本机」。
  - StoreKit 权益不在清除范围内：购买记录在苹果侧，清本地快照不等于退款。
- **DC-027 CloudKit 生产 schema 部署是 Phase 2 硬门槛**：见 FR-063。
  - 理由：Development 与 Production 是两套 schema；只在开发容器里「看起来有表」却未 Deploy to Production，是 TestFlight 同步失败的头号常见坑，且暴露时点晚、排障成本高。
  - 裁决：Checkpoint 2 未在 CloudKit Dashboard **Production** 侧确认全部 record types 之前，**MUST NOT** 进入 Phase 3。
- **DC-028 KeyHealthServing 契约在 V1 预留**：protocol 与 DTO 写入 contracts，V1 **不实现、不在 UI 暴露入口**；V2 只填实现。
  - 理由：与「健康度字段自 V1 进 schema」（FR-055）同一逻辑——契约缺口会在 V2 迫使改共享类型与依赖注入形状。预留空协议的成本接近零。
- **DC-029 删除进入「最近删除」回收站，保留 30 天**：对齐系统「密码」App。见 FR-006、SC-015。
  - **推翻的旧语义**：原先「删除 = 软删元信息 + 立即删 Keychain、明文不可再取」——那会使误删不可恢复，也与用户对「密码类产品」的预期不一致。
  - **新语义**：默认删除 = 移入回收站；Keychain **保留** 30 天；可恢复；到期或「立即删除」才毁明文。用量快照在永久清除后仍保留（与永久清除明文不矛盾）。
  - **与 FR-061 的边界**：「清除全部数据」是销毁意图，MUST 立即清空回收站，不给 30 天。
  - **额度**：回收站内不计免费额度，否则「删一把腾额度」不成立。
  - **范围**：回收站针对**密钥**（及级联进入回收站的账号下密钥）。使用方工具仍按原规则处理（非密钥资产，不做 30 天回收站）。

## 宪法修订记录

本规范原与宪法 v1.0.0 第 VII 条冲突（该版本禁止明文写入剪贴板，亦未允许明文经 iCloud 同步）。宪法已修订至 **v2.0.0**：

- **第 VII 条「密钥安全」**：剪贴板由绝对禁令改为**条件许可**（显式操作 + 身份确认 + 限时自动清除 + 风险披露）；新增允许 Keychain 的 iCloud 同步，并要求隐私表述与实际行为一致；新增管理类高权限凭证的保护与披露条款。
- **第 VIII 条**更名为「身份确认门闩」，覆盖范围扩展到复制到剪贴板与配置管理类凭证，并区分可由用户关闭与不可关闭的门闩。
- **新增第 IX 条「数据真实性」**，对应本规范 FR-015 / FR-016 / FR-019 与 US4 中「平台能力差异必须如实呈现」的要求。

宪法随后修订至 **v2.1.0**（新增「本地化」小节，对应 DC-014 与 FR-042～FR-046）。

宪法现已修订至 **v2.2.0**，对应本次新增的 DC-017～DC-025：

- **第 VII 条**新增「明文派生物 MUST NOT 进入同步存储或导出物」，对应 FR-057 放弃哈希去重的取舍。
- **第 VIII 条**新增「探活 MUST NOT 触发门闩」，并要求两类门闩例外以显式命名体现，对应 FR-053。
- **第 IX 条**新增「未知与否定必须区分」与「检查通过不得外推结论」，对应 FR-052、FR-054。
- **新增「无障碍」小节**，并修正原「MUST NOT 让 VoiceOver 读出明文」这一会排除视障用户的规则，对应 FR-059、DC-024。
- **新增「不可逆决策」小节**，集中登记 bundle id / Team ID / Keychain group / App Group / iCloud 容器 / CloudKit 生产 schema / 内购配置 / 最低系统版本，对应 DC-018、DC-023。
- **稳定性章节**：最低版本提升为 iOS 18.0 / macOS 15.0，新增 Swift 6 语言模式要求，对应 DC-019。

本规范与宪法 v2.2.0 无冲突。
