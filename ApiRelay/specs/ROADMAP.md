# ApiRelay 产品路线图

**Date**: 2026-08-04
**Status**: 已由产品负责人确认分三阶段实施
**依据**: [001-key-vault/spec.md](./001-key-vault/spec.md) · Constitution v2.3.0

> 本文是**阶段范围的唯一权威**。任何关于「某功能属于哪个阶段」的争议以本文为准。
> 每阶段独立成一条功能分支、独立可交付。
> **前一阶段未验收通过，MUST NOT 开始下一阶段的实现。**

## 术语：两类「平台」不可混淆

| 术语 | 含义 | 举例 |
|------|------|------|
| **上游平台**（API 提供方） | 签发密钥、提供模型、产生消费 | OpenAI、Anthropic、Google、OpenRouter、DeepSeek、智谱 AI、阿里百炼、火山引擎、硅基流动 |
| **使用方工具**（消费端） | 消费密钥、发起调用的客户端 | VS Code、Cursor、OpenCode、Trae |

**两类都是「内置预置清单 + 用户可自定义添加」**（FR-007a、DC-012）。

**每阶段独立上架**，一步一个脚印，不追求短期流量：

- 付费逻辑仍在 Stage 1 完成（决定数据模型与权益判断，后补会引起返工）。

## 只有一次机会的决策（必须在 V1 写业务代码前定稿）

以下决策一旦生效便无法回退，或回退代价是用户数据丢失。**它们不是「以后再优化」的选项。**
权威清单见宪法「不可逆决策」节，确切取值登记在 [001-key-vault/plan.md](./001-key-vault/plan.md) A5。

| 决策 | 一旦定错的后果 | 裁决 |
|------|---------------|------|
| Bundle ID / Team ID / Keychain group / App Group / iCloud 容器 | **Team ID 变更会让已存的全部 Keychain 条目读不出来** | DC-018：统一 `com.apirelay.*`；容器 **`iCloud.com.apirelay.ApiRelay`**（见 plan A5） |
| Swift 语言模式 | 写完再切，严格并发检查一次性产生大量错误 | DC-019：Swift 6 |
| 最低系统版本 | 上架后抬高会把已有用户挡在升级外 | DC-019：iOS 18.0 / macOS 15.0 |
| Mac 形态 | 迁到原生 macOS 会破坏 FR-005（`NSPasteboard` 无过期机制） | DC-020：Mac Catalyst |
| CloudKit 生产 schema | 字段不可删、类型不可改、类名即 record type | 十个实体 + 预留字段一次性部署 |
| 偏好项的同步归属 | 事后搬字段是跨 `ModelConfiguration` 的数据迁移 | DC-021：拆两组 |
| 用量周期的时区口径 | 事后统一口径必然违反 FR-019（不得改写历史） | DC-022：随数据记录并标注 |
| 内购的家庭共享开关与产品 ID | **家庭共享一旦开启不可关闭**；产品 ID 不可删除复用 | DC-023：产品 ID `com.apirelay.iap.unlimited_keys`；家庭共享**开启**；V3 预留 `com.apirelay.iap.relay` |
| CloudKit 生产 schema 首次部署 | 字段不可删、类型不可改；漏部署则 TestFlight 同步失败 | DC-027 / FR-063 |

## 为什么要分阶段

三个阶段的技术风险与依赖差异极大：

| 阶段 | 是否需要联网调上游 | 是否需要服务端 | 是否涉及用户请求内容 | 风险 |
|------|:---:|:---:|:---:|------|
| V1 | ❌ | ❌ | ❌ | 低 |
| V2 | ✅ | ❌ | ❌ | 中（依赖各平台接口能力与稳定性） |
| V3 | ✅ | ✅ Cloudflare Worker | ✅ **prompt 经过中转** | 高（新技术栈 + 重大隐私变更 + 部署体验） |

把三者混在一起做，V3 的风险会拖死 V1 的交付。分开做，V1 两三周就能有可用产品。

## V1 — 密钥保险库（分支 `v1` / 小迭代 `v1.N`）

**一句话**：给 API 密钥做一个比「记在备忘录里」安全得多的保管与分发工具。

**产品边界**：**完全不联网调用任何上游平台接口**。这一条决定了 V1 的全部简化——
不需要管理凭证、不需要平台适配器、不需要刷新调度、不需要通知。

### 范围

| 能力 | 说明 |
|------|------|
| 上游账号与密钥保管 | 9 家预置上游平台 + 自定义添加；同平台可多账号；明文存 Keychain，经 iCloud 钥匙串跨设备同步 |
| **最近删除回收站** | 删除密钥保留 **30 天**可恢复（对齐系统密码 App）；到期或立即删除才毁 Keychain（DC-029） |
| 掩码展示 | 列表永不出现完整明文 |
| 身份门闩取出明文 | 查看与复制共用一道门闩；四档验证方式（含应用主密码） |
| 剪贴板分发 | 自动清除默认开、用户可关（关掉须披露风险）；出厂默认 2 分钟，列表可改（2 分钟可删）；可禁用通用剪贴板；Mac 不承诺杀掉后仍清 |
| 使用方工具与指派 | 预置清单 + 自定义添加；**一把密钥可指派给多个工具（多对多）**；未指派归入「未分配」 |
| 双视角列表 | 按上游平台 / 按使用方工具，读同一份数据；共享密钥不重复计数 |
| 免费额度与买断 | 免费共 3 把；一档买断解锁无限 |
| 加密备份 | AES-GCM 导出/导入，门闩不可关闭 |
| 设置 | 安全偏好跨设备一致；外观与默认视角仅存本机、不同步（DC-021）；**清除全部数据**（DC-026） |
| 录入正确性 | 关闭自动更正/自动大写/智能标点、去空白、重复录入提示（DC-025） |
| 无障碍 | Dynamic Type、VoiceOver 标签、明文逐字符朗读（DC-024） |
| 上架工程卡点 | 加密出口声明 + `PrivacyInfo.xcprivacy`（DC-018、FR-045、FR-058） |
| CloudKit 生产 schema | Phase 2 硬门槛：Production 侧部署齐全后再写业务代码（DC-027、FR-063） |
| 契约预留 | `KeyHealthServing` 协议与健康度 DTO 在 V1 定义、不实现（DC-028） |
| Mac Catalyst | 双端可用。**形态不可改**，理由见 DC-020 |

### 明确不在 V1

用量统计、余额查询、App 内签发密钥、关系图、通知提醒、**密钥可用性检测**、中转——全部不做，
**界面上也不应出现入口**（避免用户预期落空）。

### 验收标准

用户能把现在散落在备忘录、聊天记录、配置文件里的所有 API 密钥收进来，
在需要时经身份验证复制出去，并且换设备后仍能取到。

## V2 — 用量看板与关系图（分支 `v2` / 小迭代 `v2.N`）

**一句话**：让用户知道每一把密钥、每一个工具花了多少钱。

**依赖**：V1 的数据模型与保管能力。

### 范围

| 能力 | 说明 |
|------|------|
| 管理类高权限凭证 | 配置 Admin / Management Key；门闩不可关闭；风险明确披露 |
| 四平台适配器 | OpenRouter / OpenAI / Anthropic / DeepSeek，各按其真实能力 |
| 用量与余额刷新 | 按用户设定间隔自动执行，**不需要任何身份验证** |
| 能力诚实呈现 | 平台不支持的数据显式说明，**不显示 0、不留空** |
| 费用估算 | 平台给出的数字与本产品估算分开呈现；单价规则可维护 |
| 双视角聚合 | 平台维度与使用方维度共用同一聚合实现 |
| 三类本地通知 | 余额不足 / 密钥失效 / 每周摘要 |
| App 内签发与作废密钥 | 仅 OpenRouter 支持；其余平台入口提前置灰 |
| **关系图（Mac 优先）** | 见下方专节 |
| **加密传递** | 勾选密钥生成口令加密文件，经系统分享面板交付给同事/朋友。**不经任何服务器、不可撤回**，须如实告知。复用 V1 的加密备份格式，成本极低。见 US9、DC-016 |
| **密钥可用性检测** | 手动触发（单把 / 全部），用密钥自己发一次不消耗 token 的最小请求判定是否仍被上游接受；失效的密钥在列表上带感叹号。**不需要管理凭证**，因此 DeepSeek 这类不支持按密钥统计的平台也可用。见下方专节与 US10、DC-017 |

### 关系图（新增需求，已评估为合理）

产品负责人提出「像思维导图一样，看哪些密钥用到哪些平台、哪些平台用了哪些密钥」。
**结论：合理，纳入 V2。但形态需要修正。**

**为何不做自由布局的思维导图**：本产品的数据不是网状的，而是**三层分明的**：

```text
上游平台/账号  ──1:n──▶  密钥  ──n:1──▶  使用方工具
```

由此推导出的真实基数关系是：

| 关系 | 基数 | 说明 |
|------|------|------|
| 上游平台 → 密钥 | 一对多 | 一个平台账号下多把密钥 |
| 密钥 → 上游平台 | **多对一** | 一把密钥只属于一个平台。**「一把密钥用到多个上游平台」在技术上不存在** |
| 密钥 ↔ 使用方工具 | **多对多** | 一把密钥可给多个工具；一个工具可持有多把密钥（DC-011） |
| 上游平台 ↔ 使用方 | **多对多** | 经密钥间接连接 |

因此三列布局里，**中间列到右列是多对多**（一把密钥可以连出多条线到不同工具），
左列到中间列是一对多。共享密钥（连出 ≥2 条线）在图上 MUST 有明确区分样式，
因为它的用量无法归属到单个工具（FR-008a）。

因此**三列桑基式关系图**（左：平台 / 中：密钥 / 右：使用方，用曲线连接）比自由布局的
思维导图更易读，且不需要自研力导向布局算法——后者在宪法第 III 条「零第三方 SDK」下
要从零实现，代价与收益不成比例。

**交互设计**：点击任一节点高亮其全部关联路径；连线粗细可映射用量金额（这也是把它放在 V2
而非 V1 的理由——有了用量数据，图才有信息量，否则只是一张连线图）。

**平台策略**：Mac 优先（大窗口才放得下）；iPhone 上降级为可横向滚动的紧凑版或直接隐藏入口。

### 密钥可用性检测（新增需求，已评估为合理）

产品负责人提出「能检测密钥是否还能用，不能用的加个感叹号；不用实时刷新，用户手动刷新」。
**结论：合理，纳入 V2。**

**为何不放 V1**：检测必然要联网调上游，而 V1 的定义性边界正是**完全不联网调上游**——
这一条决定了 V1 不需要 HTTPClient、不需要网络权限、不需要错误分类体系。
探活归 Stage 2；Stage 1 以 **1.0.0** 单独上架后，用户需升级到 **2.0.0** 才获得该能力（可接受的阶段边界，不是「零延迟」）。
V1 只需在数据模型里预留健康度字段（FR-055），因为 CloudKit 生产 schema 在 V1 一次性部署。

**为何它不是用量统计的附属品**：检测**只需要密钥自己**，不需要管理类高权限凭证。
这个门槛比用量统计低得多——V2 里「DeepSeek 不支持按密钥统计用量」的限制，
对检测完全不适用。因此它是一条独立的能力，不随 US4 的平台能力差异而残缺。

**必须做对的四件事**（全部是宪法第 IX 条的落点，见 FR-052、FR-054）：

| 情形 | 正确呈现 | 做错的后果 |
|------|----------|-----------|
| 从未检测过 | **无任何标记** | 加感叹号等于宣称它失效了 |
| 429 限流 | 「未能确认」 | **批量检测本身就会触发限流**，然后把自己所有密钥标成失效 |
| 断网 / 超时 / 5xx | 「未能确认」，保留上次结论与时间 | 用户一断网就看到满屏感叹号 |
| 检测通过 | 「密钥有效」 | 说「可用」是外推——余额与模型权限都没查 |

**触发方式**：仅手动，两个粒度（单把 / 当前列表全部）。批量串行且节流，同一把密钥有冷却期。
**MUST NOT 在启动或进入前台时自动执行**——那是用户没预期的网络流量，也会撞限流。

**门闩**：检测 MUST NOT 触发身份验证（FR-053）。理由与「自动刷新读管理凭证不触发门闩」相同：
明文没有交给用户，而批量检测逐次弹面容 ID 会使功能不可用。

### 验收标准

用户能回答「这个月 VS Code 花了多少钱」「哪把密钥在闲置」「哪几把已经不能用了」，
并能一眼看出密钥的分布结构。

## V3 — 中转服务（分支 `v3` / 小迭代 `v3.N`）

**一句话**：在用户自己的 Cloudflare 账号上架一层中转，让下游工具的配置**永久不用再改**。

### ⚠️ 中转的精髓（此前理解有误，已更正）

我最初把中转理解为「一把原始密钥拆成多把、实现隔离」。**这只是次要好处。**
产品负责人指出的真正精髓是**下游配置的稳定性**：

```text
【无中转】VS Code ──直连──▶ DeepSeek
          DeepSeek 密钥失效 ⇒ 必须逐个打开 VS Code、OpenCode… 改配置

【有中转】VS Code ──中转密钥──▶ 中转服务 ──原始密钥──▶ DeepSeek
          DeepSeek 密钥失效 ⇒ 只在中转服务里换掉原始密钥
                              中转密钥不变 ⇒ 所有工具配置一行都不用动
```

**中转密钥是一个稳定的间接层。** 它把「上游密钥的生命周期」与「下游工具的配置」彻底解耦。
上游可以随便换、随便轮换、甚至换成另一个账号，下游感知不到。

### 由此推出的第三个好处（同样重要）

中转服务在转发每一次请求时，天然知道**这一笔调用属于哪把中转密钥**。这意味着：

- 用量统计不再看上游平台的脸色。V2 里 DeepSeek「不支持按密钥统计」的问题，**中转一上就彻底解决**。
- 可以拿到真正的**逐笔明细**，而不只是周期聚合。

换句话说，V2 的统计能力受限于各平台参差不齐的接口；V3 的统计能力完全自主。

### V1/V2 的「一工具一密钥」是中转的降级替代

必须写清楚，否则日后容易误判「V2 已经解决问题、V3 没必要」：

| 好处 | V1/V2（平台原生多密钥） | V3（中转） |
|------|:---:|:---:|
| 一工具一密钥的隔离 | ✅ | ✅ |
| 泄露后可单独作废 | ✅ | ✅ |
| **上游轮换不动下游配置** | ❌ **做不到** | ✅ |
| 按密钥/按工具的用量 | ⚠️ 看平台能力，DeepSeek 完全不支持 | ✅ 完全自主 |
| 逐笔明细 | ❌ | ✅ |
| 不需要服务端 | ✅ | ❌ |
| 请求内容不经第三方 | ✅ | ❌ **prompt 会经过中转** |

### 范围

| 能力 | 说明 |
|------|------|
| **给他人共享（可撤销）** | 为同事/朋友签发专属中转密钥；**可单独撤销、可单独统计、可设消费上限**，对方永远拿不到原始密钥。这是 V2「加密传递」的正确升级形态 |
| Worker 部署引导 | 部署到**用户自己的** Cloudflare 账号，本产品不托管任何流量 |
| 原始密钥托管 | 原始密钥推送到用户的 Worker 存储 |
| 中转密钥签发 | 一把原始密钥签发多把中转密钥，一工具一把 |
| **原始密钥轮换** | 替换原始密钥，中转密钥与下游配置完全不变 ← 核心价值 |
| 请求转发 | 按平台协议转发推理请求，含流式响应 |
| 逐笔用量明细 | Worker 侧记账，回传 App |
| 第二档买断 | 解锁中转功能 |

### V3 的重难点（现在就要记住）

1. **技术栈扩张**：Worker 是 JS/TS，不是 Swift。宪法第 III 条「Apple 原生优先」只约束客户端，
   服务端需要单独的技术约定。项目会变成双技术栈仓库。
2. **重大隐私变更**：用户的 prompt 内容会流经中转服务。虽然是用户自己的 Cloudflare 账号，
   隐私政策、App 隐私问卷、产品内披露**全部需要重写**。这是三个阶段里唯一触及「用户内容」的一步。
3. **部署体验是最大的产品难点**：让非技术用户在自己的 Cloudflare 账号上部署一个 Worker，
   是整个 V3 成败的关键。需要引导式流程（可能借助 Cloudflare API Token 自动部署），
   而不是甩一份文档让用户自己 `wrangler deploy`。
4. **协议适配**：OpenAI 兼容协议与 Anthropic 原生协议不同，流式格式也不同。中转要按平台适配，
   且要在上游协议演进时保持兼容。
5. **原始密钥的双存储一致性**：密钥同时存在于 Keychain（App 侧）与 Worker 存储（服务端侧），
   需要设计推送与校验机制，避免两边不一致导致「App 显示正常但调用失败」。
6. **延迟与可用性**：多一跳网络。Worker 冷启动、Cloudflare 免费额度上限（超出需用户自行付费）
   都要如实告知。
7. **审核风险**：引导用户部署服务端、以及「代理 AI 请求」这个行为，可能被苹果问询。

## 分支与文档约定

```text
main                    稳定、可发布（Stage N 上架后合并；tag release/N.0.0）
├── v1 / v1.N           Stage 1 密钥库（旧名 v0.1 / v0.1.N）
├── v2 / v2.N           Stage 2 用量（旧名 v0.2 / v0.2.N；从已发布的 main 或 v1 tip 切出）
├── v3 / v3.N           Stage 3 中转（旧名 v0.3 / v0.3.N）
└── plan / plan.N       规划线（旧名 v0.0 / v0.0.N）
```

小迭代命名与上传硬规则见 [playbooks/BRANCHES.md](./playbooks/BRANCHES.md)。

```text
specs/
├── ROADMAP.md              ← 本文，阶段范围的唯一权威
├── 001-key-vault/          ← 文档目录（含全产品规范 + V1 的 plan/tasks）；不是 Git 分支名
│   ├── spec.md             全产品需求，每条标注所属阶段
│   ├── research.md         技术调研（跨阶段）
│   ├── data-model.md       数据模型（含 V2/V3 扩展点）
│   ├── contracts/          接口契约
│   ├── plan.md             V1 实现计划
│   ├── tasks.md            V1 任务拆解
│   └── checklists/
├── 002-usage-insights/     ← 启动 V2 时创建，只写增量（文档目录）
└── 003-relay-service/      ← 启动 V3 时创建，只写增量（文档目录）
```

**为何 `spec.md` 与 `data-model.md` 覆盖全三阶段而不拆分**：数据模型必须一次性按三个阶段设计，
才能保证 V2/V3 不产生破坏性迁移（见 data-model.md §10 的三个扩展点）。若按阶段拆分数据模型，
到 V3 时必然要推倒重来——这正是产品负责人明确要避免的事。

**V2/V3 的 spec 只写增量**：新增需求、新增适配细节、新增契约，数据模型继承 V1 的定义并只做
additive 扩展。
