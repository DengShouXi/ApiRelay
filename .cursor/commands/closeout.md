## 第一步

仅在改动 App 源码、App 测试或构建配置时执行下面的命令。报告退出码和关键失败信息；原始长日志可保留在工作包，不必全文贴进对话：

```bash
bash ApiRelay/scripts/selfcheck.sh
```

红线项有失败就停下并说明，不能报告验收通过。

## 第二步

App 相关改动逐条回答四问；未涉及的项目写“不适用”并简述原因，不合并成一句空泛结论：

1. **外部资源**：本次改动新增或碰到了哪些进程级共享资源
   （Keychain / SwiftData / CloudKit / UserDefaults / App Group 容器 / 文件系统 / StoreKit）？
   每一样在测试里怎么隔离？

2. **失败路径**：本次加的功能有前提吗？前提不成立时用户看到什么、怎么自己走出来？
   这个功能有几种失败，用户分得清吗？

3. **接缝**：新加的 protocol 有测试替身吗？没有的话，相关测试是不是只能用真零件？

4. **文件粒度**：本次改的文件超过 400 行了吗？超了就点名，但**不要动手拆**。
